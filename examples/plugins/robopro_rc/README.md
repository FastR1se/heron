# robopro-rc

Пакет манипуляторов серии RC «Робопро» (бывш. Rozum Robotics), первый робот **командного** класса
интерфейса на железе (фаза 5). Устроен как пакет, который пользователь пишет для API своего робота
(ADR-0056): начат заготовкой `profile new robopro_rc --control-mode command`, проверяется общим
контрактным набором из своих тестов, импортирует из платформы только публичный API.

| Точка входа | Что это |
|---|---|
| `adapters: robopro_rc` | адаптер командного класса поверх `RobotApi` производителя (API 1.4.1) |

Двойника нет: у производителя нет симулятора. Мир робота — `dummy` в командном режиме, миссия уходит
на железо целью `real` (ADR-0051).

## Установка

```bash
uv pip install -e examples/plugins/robopro_rc
```

Этого достаточно для тестов: всё, что решает адаптер, проверяется на записывающем канале. Живой связи
нужен архив API «Робопро» версии **1.4.1** (Python 3.10–3.13; зависимости — numpy и scipy):
`pip install <каталог архива>`. Архив в репозиторий не кладётся — лицензии в нём нет.

## Связь

`params` адаптера `real` в профиле (`examples/robots/rc5/profile.yaml`):

| Ключ | Обязателен | Смысл |
|---|---|---|
| `host` | да | IPv4 контроллера; по руководству ввода — `192.168.10.10` |
| `model` | да | модель ровно так, как её возвращает `get_robot_info` — удостоверение тела (ADR-0054). До пробы 0.22 в профиле `null`, и `connect` отказывает, называя пробу |
| `link_timeout` | нет | сколько ждать первого пакета RTD после подключения, с (5) |
| `poll_timeout` | нет | сколько ждать нового пакета в такте, с (0.1) |

## Что решает адаптер

- **Отказ до отправки** (`CommandRefusedError`, ADR-0026): цель вне `limits.joint_position`; статус
  безопасности не `normal`/`reduced`; контроллер не в `run`; движение ещё идёт; применённая шкала скорости
  больше запрошенной. Отказ контроллера в точке (буфер, достижимость, сингулярность) — тоже отказ: счётчик
  точек не сдвинулся, в буфере ничего нет.
- **Скорость и ускорение** — из рамки профиля, одно значение на точку (API берёт одно на все суставы):
  наименьшее по суставам. Шкала прогона — `scale_setup.set(s, s²)` (ADR-0057), обе применённые шкалы
  читаются обратно и сверяются.
- **Фаза движения** (ADR-0049): из одного пакета RTD — `wp_cntr`, `buff_fill`, `motion_mode`, `safety`,
  состояние контроллера. Движение защёлкнуто от принятия точки до пакета, в котором контроллер взял именно
  эту точку, буфер пуст и режим снова `hold`.
- **Метка** — `sec`/`nsec` контроллера (ADR-0050). Статусы и шкала — в `RobotState.extra`.
- **Аварийный останов** — `hold`: удержание, буфер сброшен, питание и тормоза не трогаются (ADR-P5A).
  Без связи останавливать нечем — адаптер это говорит, а не скрывает.
- **Тормоза снимает человек** в «Пульсе»; адаптер состояние питания не меняет, подтверждение позиции всегда
  отвергает (ADR-0054).

## SDK, который владеет процессом (ADR-0053, ADR-P5B)

`RobotApi` создаётся только при подключении, с `ignore_controller_exceptions=True` и логгером процесса;
прежний `sys.excepthook` возвращается сразу после создания; `disconnect` SDK — на любом пути. Пакет RTD
читается закрытым приёмником SDK (`_rtd_receiver`) — открытого чтения пакета целиком у API нет; поэтому
версия закреплена требованием `API ==1.4.1`, а каждое показание сверяет маркеры пакета.

## Кинематика (ADR-0055)

`examples/robots/rc5/rc5.urdf` написан руками по таблице DH из API; соглашение DH — **предположение**
(классическое). Проверка — на роботе: проба пишет пары `act_q`/`act_flange_x`, и

```bash
python -m robopro_rc.kinematics pairs.json --urdf examples/robots/rc5/rc5.urdf
```

печатает худшее расхождение описания, классической и модифицированной DH по положению и ориентации.
