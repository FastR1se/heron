# Heron — платформа моделирования гетерогенных робототехнических комплексов

> Рабочее имя `heron` (**H**eterogeneous **R**obotics **En**vironment) — временное. Правила из раздела 17 держат переименование в пределах одной операции, в том числе после того, как код написан.

Документ описывает утверждённую архитектуру. Это источник правды: любое решение в коде, противоречащее разделам «Инварианты» и «Абстракции ядра», считается ошибкой, а не компромиссом.

---

## 1. Что это и зачем

**Проблема.** Разработка гетерогенного комплекса сегодня — это ручная склейка несовместимых сред. Модель робота существует в трёх форматах (URDF, SDF, USD), обучение живёт отдельно от исполнения, перенос политики на железо каждый раз пишется заново, а ошибки согласования (порядок суставов, единицы, частоты) проявляются только на реальном роботе.

**Решение.** Платформа формализует полный жизненный цикл: описание → генерация сред → программирование или обучение навыка → проверка в симуляции → исполнение на комплексе → перенос на оборудование. ROS 2 используется как слой коммуникации и исполнения, а не как замена платформе.

**Отличие от чистого ROS 2.**

| Задача | Только ROS 2 | Heron |
|---|---|---|
| Описание робота | URDF, SDF, USD и конфиги ведутся раздельно и расходятся | Один профиль, остальное генерируется |
| Обучение | Внешний мир, ROS 2 о нём не знает | Часть конвейера, среда собирается из сценария |
| Перенос политики | Свой узел под каждый проект | ONNX + контракт автоматически становятся навыком |
| Согласование сред | Проверяется глазами, ошибки молчаливые | Валидатор ловит до запуска |
| Код и обучение | Разные сущности | Один интерфейс навыка |
| Описание комплекса | Launch-файлы и compose вручную | Один сценарий, всё генерируется |

**Границы (чего платформа не делает).** Не заменяет ROS 2, симуляторы и RL-библиотеки. Не пишет функцию награды — её пишет человек по шаблону. Не гарантирует перенос без потерь: она измеряет разрыв, а не устраняет его. Не является средой исполнения реального времени.

## 2. Инварианты

Семь правил. Нарушение любого — повод остановиться и переделать.

1. **В ядре нет имён роботов.** Ни `if robot == "g1"`, ни импортов вендорских SDK. Проверка: удаляем `robots/` — ядро собирается и проходит тесты.
2. **Границы миров — файлы.** Из Isaac Lab наружу выходят только артефакты (ONNX + контракт). Никаких живых связей между окружением обучения и окружением исполнения.
3. **Один образ — две среды.** Контейнер робота одинаков в симуляции и на железе. Меняется только конфиг адаптера.
4. **Миссия не знает, как сделан навык.** Замена кодового навыка на обученный — правка одной строки в профиле.
5. **Профиль — данные, не код.** Добавление робота не требует правок в ядре: только YAML-профиль и, при необходимости, плагин-адаптер снаружи.
6. **Контракт проверяется до запуска.** Любое рассогласование сред — ошибка валидатора, а не странное поведение робота.
7. **Возможности, а не типы.** Ядро не знает понятий «гуманоид» и «манипулятор». Оно знает, что робот умеет.

## 3. Доменная модель

| Сущность | Что это |
|---|---|
| **RobotProfile** | Полное декларативное описание робота: кинематика, контракт, возможности, адаптер |
| **Contract** | Соглашение о представлении данных между средами: порядок суставов, единицы, частоты, лимиты |
| **Capability** | Атомарная способность робота (`base.velocity`, `arm.joint_position`, `gripper.binary`) |
| **Skill** | Единица поведения с общим интерфейсом. Реализация — код или политика |
| **Scenario** | Описание комплекса: мир, состав роботов, роли, задачи |
| **Mission** | Сценарий работы комплекса на Python поверх SDK |
| **ControlAdapter** | Плагин связи с конкретным роботом или его симуляционным двойником |
| **SimBackend** | Плагин симуляционной среды |
| **TrainBackend** | Плагин среды обучения |
| **Artifact** | Версионированный результат: политика, чекпоинт, запись прогона, отчёт |

### Модель возможностей

Ключ к гетерогенности. Навык объявляет требуемые возможности, робот — доступные, платформа проверяет пересечение.

```
base.velocity          # команда линейной и угловой скорости
base.pose              # перемещение в целевую позу
arm.joint_position     # позиции суставов
arm.joint_torque       # моменты
arm.cartesian          # поза конечного звена
gripper.binary         # открыть/закрыть
gripper.width          # ширина раскрытия
whole_body.torque      # низкоуровневое управление всем телом
```

Ключ — ровно два сегмента `<домен>.<аспект>`, реестр ключей в ядре закрыт,
возможности сторонних роботов живут в домене с префиксом `x_` (`x_unitree.dance_mode`).
Параметров возможность не несёт: степени свободы, единицы и диапазоны уже заданы в
контракте и лимитах, дублировать их — значит завести второй источник правды ровно для
тех величин, расхождение которых платформа и ловит. Количественные требования навык
объявляет отдельным блоком `requires`, валидатор сверяет его с контрактом и лимитами
профиля (ADR-0001).

### Режим управления

Ортогонален возможностям и критичен для реализуемости навыка:

- `streaming` — принимает поток команд на заданной частоте (`ros2_control`, DDS-SDK). Пригоден для обученных политик.
- `command` — принимает команду «выполни движение» и сообщает о завершении (REST-API). Политики с циклом 50 Гц неисполнимы.

Валидатор обязан отклонить навык, требующий `streaming`, на роботе с `command`.

### Уровень доступа

Для роботов со встроенными контроллерами (гуманоиды):

- `high` — встроенный контроллер выполняет команды верхнего уровня
- `partial` — встроенный контроллер держит баланс, пользователь управляет частью тела
- `low` — полное управление, встроенный контроллер отключён; взаимоисключающе с `high`

## 4. Слои

```
Интерфейсы     CLI · Python SDK · Foxglove (визуализация, готовый компонент)
     │
Ядро           Registry · Scenario · Skills · Validator · Generators · Store
     │
     ├── Обучение (изолированное окружение): EnvBuilder → Trainer → Exporter
     │
     └── Исполнение (ROS 2): Coordinator → контейнеры роботов (Executor · Skills · ControlAdapter)
                                    │
Мир                        Gazebo · MuJoCo · Реальное железо
```

**Состав ядра.**

- **Registry** — реестр профилей роботов и их версий.
- **Scenario** — разбор и валидация описаний комплекса.
- **Skills** — библиотека навыков с версиями и требованиями к возможностям.
- **Validator** — сверка контрактов, возможностей, режимов, лимитов. Центральный компонент новизны.
- **Generators** — из профиля и сценария порождают то, что выводимо: блок `ros2_control` и конфигурацию контроллеров, мир Gazebo, конфиг среды Isaac Lab, файлы запуска ROS 2, конфигурацию визуализации, docker-compose. Описание кинематики (`description.urdf`) и заданный сценарием мир — **вход** платформы, а не выход: генератор их не сочиняет и не перезаписывает, а валидатор сверяет описание с профилем (ADR-0009, ADR-0010).
- **Store** — файловое хранилище артефактов с версиями и JSON-метаданными.

**Контейнер робота** (единица развёртывания, один образ на тип робота):
`Executor` (исполняет задачи последовательностью навыков) → `Skills` (код и ONNX) → `ControlAdapter` (говорит с железом или симулятором).

**Координатор** — отдельный контейнер: очередь задач, распределение по возможностям роботов, контроль выполнения.

## 5. Абстракции ядра

Четыре точки расширения. Всё вендорское реализует эти протоколы снаружи.

```python
class ControlAdapter(Protocol):
    """Связь с конкретным роботом или его двойником в симуляторе."""
    def connect(self, profile: RobotProfile, config: dict) -> None: ...
    def disconnect(self) -> None: ...
    def read_state(self) -> RobotState: ...
    def send_command(self, cmd: Command) -> None: ...
    def capabilities(self) -> set[Capability]: ...
    def control_mode(self) -> ControlMode: ...
    def safety_limits(self) -> Limits: ...
    def emergency_stop(self) -> None: ...

class Skill(Protocol):
    """Единица поведения. Код и политика неразличимы снаружи."""
    required_capabilities: set[Capability]
    required_control_mode: ControlMode

    def start(self, goal: dict, ctx: SkillContext) -> None: ...
    def tick(self, state: RobotState) -> Status: ...   # RUNNING | SUCCESS | FAILURE
    def cancel(self) -> None: ...

class SimBackend(Protocol):
    """Симуляционная среда."""
    def build_world(self, scenario: Scenario) -> WorldHandle: ...
    def spawn(self, profile: RobotProfile, pose: Pose) -> RobotHandle: ...
    def start(self) -> None: ...
    def stop(self) -> None: ...

class TrainBackend(Protocol):
    """Среда обучения."""
    def build_env(self, scenario: Scenario, learner: str) -> EnvHandle: ...
    def train(self, cfg: TrainConfig) -> Checkpoint: ...
    def export(self, ckpt: Checkpoint) -> PolicyArtifact: ...   # ONNX + контракт
```

`LearnedSkill` — единственная реализация `Skill` в ядре: принимает `PolicyArtifact`, сверяет его контракт с профилем робота, крутит ONNX в цикле. Все обученные навыки — её экземпляры.

Отказ адаптера в команде — штатный исход `send_command`, и протокол его называет: `CommandRefusedError`, команда не отправлена (ADR-0026). Исполнитель на отказ сначала останавливает робота, потом завершает навык отказом с причиной; любое другое исключение тоже сначала останавливает робота, но остаётся исключением.

**Сторона двойника — пятая точка расширения** (ADR-0021). Адаптер — только одна сторона связи; в симуляции другую сторону держит двойник, говорящий протоколом робота. Пакет робота поставляет пару: адаптер на все среды и двойник для пары «адаптер, бэкенд». Двойник объявляет, какие процессы поднять, какого он рода — владеющий физикой (целый симулятор производителя, сцена из одного робота) или мост в чужой физике — и что ему нужно от окружения. Конфигурацию связи он читает из `params` адаптера. Встроенный путь `ros2_control` в Gazebo — такой же двойник, зарегистрированный той же группой. Бэкенд симуляции выбирается через плагины, а MuJoCo-бэкенд общий и протокола робота не знает.

Протокол двойника двухслойный (ADR-0024). В ядре — общая часть: за какой адаптер и в каком бэкенде двойник отвечает и какого он рода. Вклад в сцену формулирует бэкенд на своём языке: двойник в Gazebo добавляет элементы в копию описания, файлы, узлы запуска и называет имена управляющего слоя; двойник-симулятор для MuJoCo — процесс с аргументами. Пакет робота импортирует из платформы только модули публичного API (`PUBLIC_MODULES`), и это проверяет тест.

**Требования к окружению объявляет каждая сторона связи** (ADR-0025): член `requirements` у адаптера и у двойника — значения `Requirement` из закрытого реестра видов (модуль Python, пакет ROS 2, программа, переменная окружения), с условием версии по PEP 440, «нужно» или «запрещено» с причиной и подсказкой, чем это ставить. У сторон разные процессы и часто разные машины, поэтому объявления два. Проверяется машина, а не данные: `validate` окружения не касается, `env check` проверяет сцену целиком, `sim run` — сторону двойников до запуска мира, `run` — сторону адаптера до подключения. Встроенные адаптер и двойник `ros2_control` объявляют свои требования тем же способом, выводом из того, что их код использует.

**Первый пакет робота — G1 через DDS производителя** (`examples/plugins/unitree_g1`, ADR-0027–0029). Отдельный дистрибутив, найденный через ту же группу точек входа, что и встроенные адаптеры; из платформы он импортирует только публичный API. Всё, что знает об интерфейсе производителя, живёт в пакете: раскладка слотов моторов по именам, удостоверение тела на связи по `mode_machine`, закон привода с коэффициентами контракта в каждой команде, останов демпфированием. Канал связи отдаёт и принимает значения, а CycloneDDS и SDK производителя загружаются только при открытии связи, поэтому решения адаптера проверяются на машине без них — тем же общим контрактным набором, что и встроенные адаптеры.

## 6. Профиль робота

Единый источник правды. Чистые данные, ни строчки кода.

```yaml
schema_version: 1
name: pulse_75
description:
  urdf: urdf/pulse_75.urdf.xacro
  mesh_dir: meshes/

contract:
  revision: 1
  joint_order: [joint0, joint1, joint2, joint3, joint4, joint5]
  angle_unit: rad
  state_rate_hz: 100
  command_rate_hz: 10
  observation:
    - {type: joint_pos, scale: 1.0}
    - {type: joint_vel, scale: 0.05}
  action:
    type: joint_position
    clip: [-1.0, 1.0]

capabilities: [arm.joint_position, arm.cartesian, gripper.binary]
control_mode: command
access_levels: [high]

limits:
  joint_position: {min: [...], max: [...]}
  joint_velocity: {max: [...]}
  cartesian_velocity_max: 0.25

adapters:
  sim.gazebo: {plugin: heron.adapters.gz_ros2_control, params: {...}}
  real:       {plugin: heron_pulse.adapter,           params: {host: "http://10.10.10.20:8081"}}

skills: [go_home, pick, place]
image: heron/robot-arm:latest
```

**Контракт — сердце платформы.** Он сопровождает политику при экспорте и проверяется при каждом использовании. Именно его рассогласование даёт классическую ошибку «робот сходит с ума без единой записи в логах».

Поэтому у контракта своя идентичность, не зависящая от версии профиля: `contract_id` —
хеш нормативных полей (порядок суставов, единицы, состав наблюдений со шкалами,
спецификация действия, частоты). Политика и траектория хранят идентификатор, под которым
созданы, совместимость — его равенство, а при расхождении валидатор показывает различие по
полям. Поле `revision` рядом — объявление намерения: содержимое изменилось, а `revision`
нет — ошибка валидатора (ADR-0004).

## 7. Сценарий

```yaml
schema_version: 1
name: warehouse_demo
world: {backend: gazebo, file: worlds/warehouse.sdf}

robots:
  - {id: arm1,  profile: pulse_75, pose: [0, 0, 0.8],  role: learner}
  - {id: rover1, profile: humanoid_x, pose: [2, 1, 0], role: frozen, policy: walk_v3}
  - {id: box,    profile: static_obstacle, pose: [1, 1, 0], role: static}

task: {skill: reach, target: random_in_box}
```

**Роли в обучении.** `learner` — получает действия от RL-алгоритма. `frozen` — крутит готовую политику. `scripted` — простая логика внутри симулятора. `replay` — воспроизводит записанную траекторию из прошлого прогона. `static` — препятствие.

Ограничение принято сознательно: во время обучения соседи не управляются кодом ROS 2 — симулятор обучения работает быстрее реального времени и не синхронизируется с внешними узлами.

**Один владелец физики.** `world.backend` единственный: все роботы сценария обязаны иметь
адаптер под этот бэкенд, отсутствие — ошибка валидатора до запуска. Сцена из двух физических
движков невозможна не по недоделке, а по существу: движки не разделяют разрешение контактов,
поэтому взаимодействие федеративных роботов лишено смысла. Кросс-симуляторность
последовательная — одна политика в двух мирах по очереди, расхождение измеряется (ADR-0002).

**Траектории для `replay`.** Запись прогона на стороне исполнения — MCAP (rosbag2), артефакт
обучения — плотные массивы `.npz` с тем же контрактом, что носит политика; между ними одно
явное преобразование через CLI. ROS 2 в окружение обучения не попадает (ADR-0003).

## 8. Потоки

**Добавление робота.** `heron new-robot` создаёт заготовку профиля и адаптера → заполняешь → `heron add-robot` → валидатор проверяет URDF, контракт, лимиты → генераторы порождают артефакты сред → робот появляется в симуляторе и визуализации.

**Программирование навыка.** Класс на Python поверх SDK → регистрация с объявлением требуемых возможностей → привязка к профилю → отладка в симуляции.

**Обучение навыка.** Сценарий с ролями → генерация конфига среды → сборка среды и обучение с рандомизацией → экспорт ONNX + контракт → сверка контракта с профилем → навык в библиотеке → sim2sim-проверка в другом симуляторе.

**Запуск комплекса.** Сценарий → генерация docker-compose и launch-файлов → поднимается мир → стартуют контейнеры роботов → миссия через SDK → координатор раздаёт задачи → мониторинг и запись прогона.

**Перенос на железо.** `heron deploy --target real` → валидатор проверяет контракт, лимиты и уровень доступа → те же образы на бортовых компьютерах → адаптер переключается с симуляционного на реальный → та же миссия без правок → сравнение метрик sim и real.

**Цикл улучшения.** Записи прогонов → траектории соседей в обучении → дообучение → новая версия политики → навык обновляется, миссия не меняется.

## 9. Расширяемость

Плагины через штатные точки входа Python. Установка стороннего пакета добавляет робота без единой правки в ядре.

```toml
[project.entry-points."heron.adapters"]
my_robot = "my_package.adapter:MyAdapter"

[project.entry-points."heron.sim_backends"]
webots = "my_package.sim:WebotsBackend"

[project.entry-points."heron.twins"]
my_robot_gazebo = "my_package.twin:MyRobotGazeboTwin"
```

`heron new-robot <name>` порождает заготовку профиля, скелет адаптера с TODO и тест на соответствие контракту. Это и есть штатная процедура добавления своего робота.

**Опорные реализации** (в `examples/`, не в ядре) покрывают три класса интерфейсов, чтобы абстракция не оказалась заточена под один случай:

| Класс | Пример | Особенность |
|---|---|---|
| `ros2_control` | Коллаборативный манипулятор в Gazebo | Реалтайм, стандартный путь |
| Вендорский DDS-SDK | Гуманоид | Свой транспорт, уровни доступа |
| Сетевой API | Манипулятор по REST | Командный режим, не реалтайм |
| Заглушка `dummy` | Без железа | Для CI и знакомства с платформой |

## 12. Безопасность

Не раздел документации, а функция платформы.

- Валидатор проверяет лимиты суставов, скоростей и рабочей зоны перед любым запуском на железе.
- Для роботов с уровнями доступа проверяется текущий режим: низкоуровневое управление несовместимо со встроенным контроллером.
- `ControlAdapter` обязан реализовать `emergency_stop()`.
- Сторожевой таймер: пропажа состояния дольше порога — остановка.
- Первый запуск на железе — в замедленном режиме (`--speed-scale`).
- Двуногие роботы на страховочном подвесе. Кобботы — с ограничением скорости и физической кнопкой останова.

## 13. Проверка и оценка

**Тесты.** Юнит-тесты ядра без железа и симуляторов. Контрактные тесты: каждый адаптер прогоняется через общий набор проверок. Интеграционные — на `dummy` и в Gazebo. CI гоняет всё, кроме Isaac и железа.

**Эксперименты для оценки (каркас экспериментальной главы):**

1. **Разрыв sim2sim** — одна политика в двух симуляторах, метрики расхождения.
2. **Разрыв sim2real** — та же политика на железе.
3. **Трудозатраты** — добавление нового робота и перенос навыка вручную против платформы: число файлов, строк склеивающего кода, время.
4. **Эффективность валидатора** — намеренно внесённые ошибки контракта, доля пойманных до запуска.
5. **Масштабирование** — рост числа роботов в комплексе, нагрузка и задержки.

## 15. Сознательно отложено

Совместное мультиагентное обучение. Переход на следующую мажорную версию Isaac Lab. Деревья поведения вместо последовательности навыков. Тонкая настройка сети ROS 2 между контейнерами (DDS/Zenoh). Сборки под ARM для бортовых компьютеров. Собственный веб-дашборд. Kubernetes.

Всё перечисленное — раздел «Перспективы развития», а не недоделки.

сцены роботов из разных симуляторов (ADR-0002) и обучение локомоции (ADR-0005, другая целевая

## 16. Закрытые вопросы

Вопросы первой редакции закрыты записями в `docs/decisions/` 12.09.2026. Здесь только итог:
обоснование, отвергнутые альтернативы и последствия — в карточках, и новые вопросы заводятся
тоже там, а не здесь.

| Вопрос | Итог | Запись |
|---|---|---|
| Формат возможностей | Плоское двухсегментное пространство имён, закрытый реестр, никаких параметров внутри; количественные требования — блок `requires` против контракта и лимитов | ADR-0001 |
| Роботы из разных симуляторов в одной сцене | Одна сцена — один владелец физики; федерация миров — не-цель; кросс-симуляторность последовательная и измеряемая | ADR-0002 |
| Формат траекторий для `replay` | MCAP на исполнении, `.npz` с контрактом в обучении, одно явное преобразование | ADR-0003 |
| Версионность контракта | Своя, выводимая из содержимого: `contract_id` как хеш нормативных полей плюс заявленный `revision` | ADR-0004 |
| Ресурсы на обучение | Локомоция вне объёма; один ноутбук, родная Ubuntu, Isaac под измеренным порогом, запасной путь — MuJoCo | ADR-0005 |

Общий принцип, проявившийся во всех пяти: величина описывается один раз и в том месте, где она
достоверна. Параметры не дублируются в возможностях, потому что уже есть в контракте.
Совместимость выводится из содержимого контракта, а не из номера рядом. Физикой владеет один
движок, а не согласованная пара. Знание о том, что умеет контроллер, объявляет адаптер, а не
правило вывода в ядре.

## 17. Имя проекта и переименование

Имя временное. Чтобы смена имени на любой стадии оставалась механической операцией, а не рефакторингом, действуют правила.

**Одна точка правды.** Модуль `src/heron/core/branding.py` объявляет имя и всё производное от него:

```python
APP_NAME = "heron"                    # пакет, CLI, префикс точек входа
APP_TITLE = "Heron"                   # для вывода пользователю
ENV_PREFIX = APP_NAME.upper()         # HERON_HOME, HERON_STORE
ENTRY_POINT_GROUPS = {
    "adapters":     f"{APP_NAME}.adapters",
    "sim":          f"{APP_NAME}.sim_backends",
    "train":        f"{APP_NAME}.train_backends",
    "skills":       f"{APP_NAME}.skills",
}
DOCKER_NAMESPACE = APP_NAME
```

Нигде в коде имя не пишется литералом: ни в сообщениях CLI, ни в путях, ни в именах переменных окружения, ни в поиске плагинов. Всё читается отсюда.

**Правила, которые надо соблюдать с первого коммита.**

- Имя не встречается в схемах данных: в профилях и сценариях нет полей вида `heron_version`, только `schema_version`.
- Пути к данным берутся из переменной окружения через `ENV_PREFIX`, значение по умолчанию — `~/.local/share/<APP_NAME>`.
- Имена ROS 2 топиков и узлов не содержат имени платформы: пространства имён строятся от идентификатора робота.
- В именах образов Docker имя платформы подставляется из `DOCKER_NAMESPACE`, в Dockerfile — через аргумент сборки.
- Плагины сторонних разработчиков объявляют группу точек входа строкой в своём `pyproject.toml`. Это единственное место, где имя жёстко зафиксировано вне проекта, поэтому при переименовании обе группы (старая и новая) поддерживаются один релиз, а старая помечается устаревшей.
- Имя пакета Python (`src/heron/`) и имя репозитория меняются последними: это переименование каталога плюс правка `pyproject.toml`.

**Процедура смены имени.**

1. Правим `branding.py` и имя каталога пакета.
2. Правим `pyproject.toml`: имя проекта, скрипт CLI, группы точек входа.
3. Прогоняем `rg -i "<старое имя>"` по репозиторию — попаданий должно не остаться нигде, кроме `CHANGELOG` и истории.
4. Добавляем алиас старой команды CLI и старой группы точек входа на один релиз.
5. Переименовываем репозиторий; GitHub сохраняет перенаправление со старого адреса.

Пока проект не опубликован, шаги 4 и 5 не нужны: переименование сводится к правке одного модуля и одного каталога.

## 18. Журнал работы и решений

Работа исследовательская, поэтому ход разработки — такой же результат, как код. Текст пояснительной записки должен собираться из журналов, а не сочиняться заново в конце. Правило простое: **записи делаются в момент события, а не восстанавливаются потом по памяти и коммитам**.

### Четыре журнала

| Файл | Что фиксирует | Когда пополняется |
|---|---|---|
| `docs/journal/YYYY-MM-DD.md` | Ход работы: что делалось, что получилось, что не вышло и почему | Каждая рабочая сессия |
| `docs/decisions/NNNN-<тема>.md` | Архитектурные решения с альтернативами и обоснованием | При любом выборе, влияющем на структуру |
| `docs/experiments/NNNN-<тема>.md` | Постановка, условия, числа, выводы | Каждый измерительный прогон |
| `CHANGELOG.md` | Что изменилось для пользователя платформы | Каждая завершённая фаза |

### Журнал хода работы

Одна запись на сессию, в конце сессии. Формат намеренно короткий, чтобы его реально вели:

```markdown
# 2026-09-14

## Задача
Что планировалось сделать.

## Сделано
Перечень с ссылками на коммиты.

## Проблемы и тупики
С чем столкнулся, сколько времени ушло, чем закончилось.
Неудачные попытки записываются обязательно, даже если в коде от них не осталось следа.

## Наблюдения
Неочевидные факты о средах, поведении роботов, ограничениях инструментов.

## Дальше
Следующий шаг и открытые вопросы.
```

Раздел «Проблемы и тупики» — самый ценный для записки и самый уязвимый: именно его тянет пропустить. Отрицательный результат (подход не сработал, версии несовместимы, ограничение оказалось принципиальным) — это материал главы об обосновании решений. Без него вместо исследования получается отчёт о программировании.

### Журнал решений

Короткая карточка на каждое решение, влияющее на структуру. Нумерация сквозная, записи не редактируются задним числом: изменение решения оформляется новой записью со ссылкой на предыдущую и статусом «заменяет».

```markdown
# 0007. Режим управления как отдельная характеристика робота

Статус: принято | заменено записью NNNN
Дата: 2026-09-14
Контекст: часть роботов не принимает поток команд на высокой частоте.
Решение: ввести поле control_mode со значениями streaming и command.
Альтернативы: (1) считать все роботы потоковыми и обрабатывать сбой во время работы;
              (2) вывести режим из типа адаптера.
Последствия: валидатор отклоняет несовместимые навыки до запуска;
             профиль усложняется на одно поле.
```

Прямая польза: раздел записки об обосновании проектных решений собирается из этих карточек почти без переписывания.

### Журнал экспериментов

Заводится на каждый измерительный прогон из раздела 13. Обязательно фиксируются: версии всех сред, конфигурация машины, зерно генератора случайных чисел, идентификатор артефакта политики, сырые числа и путь к записи прогона. Воспроизводимость — требование, а не пожелание.

Часть этих данных платформа умеет записывать сама: `Store` при каждом прогоне сохраняет метаданные и метрики. Ручной остаётся интерпретация.

### Связь с разработкой

- Запись в журнал хода работы — часть определения готовности задачи, а не отдельное дело «на потом».
- Коммиты ссылаются на номер решения, если оно применяется: `feat(core): control_mode в профиле (ADR-0007)`.
- Закрытие фазы из раздела 14 сопровождается записью в `CHANGELOG.md` и кратким итогом: что доказано, что осталось.
- Артефакты для записки (гифки, графики, снимки экрана) складываются в `docs/media/` сразу при получении. Переснять момент, когда что-то заработало впервые, потом невозможно.
- В инструкции для агента разработки (`CLAUDE.md`) правило ведения журналов дублируется явно, чтобы записи появлялись автоматически по ходу работы.
