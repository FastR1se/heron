# План: фаза 4 — G1 через DDS производителя (MuJoCo как эталон, мост в Gazebo)

Решения, на которых стоит план, — [ADR-0020](../decisions/0020-humanoid-joins-the-system-through-vendor-dds.md)
(как гуманоид входит в комплекс) и [ADR-0021](../decisions/0021-robot-ships-as-adapter-and-twin.md)
(робот поставляется парой «адаптер и сторона двойника»).
План — рабочий документ следующих сессий, а не карточка: по ходу он уточняется, а
каждый структурный выбор внутри него оформляется своей карточкой.

---

## Цель и критерий закрытия фазы

**Тезис фазы 4:** второй робот с принципиально иным интерфейсом, абстракция доказана —
причём доказана для любого робота, чей производитель дал адаптер и двойник, а не только
для G1 (ADR-0021).

Фаза закрыта, когда на Linux-машине выполнено всё:

1. Навык `move_joints` двигает G1 **в MuJoCo** через DDS-адаптер (двойник производителя).
2. Тот же навык, тот же адаптер без изменения кода двигают G1 **в Gazebo** через наш
   DDS-мост. Между прогонами меняется только конфигурация связи.
3. Сверка двух двойников записана в `docs/experiments/0001-*.md` с числами.
4. Сценарий комплекса: манипулятор `arm6` и G1 через DDS в **одной** сцене Gazebo.
5. DDS-адаптер проходит общий контрактный набор тестов адаптеров (`tests/test_adapter_contract.py`).
6. Ядро не знает имени робота: CI-задача «ядро без `examples/`» зелёная.
7. **Пакет G1 — отдельный дистрибутив** в `examples/plugins/unitree_g1/`: адаптер и оба
   двойника объявлены точками входа, из платформы импортируется только публичный API, и
   это проверяет тест.
8. `sim run` выбирает бэкенд через плагины; MuJoCo-бэкенд общий и не знает протокола ни
   одного робота; встроенный путь `ros2_control` зарегистрирован как двойник той же
   группой.
9. Гифка в `docs/media/`, запись `[0.4.0]` в `CHANGELOG.md`, README обновлён.

## Схема

```
  платформа (общее)                          пакет unitree_g1 (как от производителя)
  ─────────────────                          ─────────────────────────────────────────
  sim run → бэкенд из sim_backends           адаптер DDS          (один на все среды)
    ├── gazebo  ── двойники рода «мост» ◄─── двойник gazebo: мост ros2_control на C++
    │              (встроенный ros2_control)
    └── mujoco  ── двойник, владеющий  ◄──── двойник mujoco: unitree_mujoco
                   физикой: сцена из
                   одного робота
  валидатор: адаптер и двойник под бэкенд, род двойника, требования окружения

                      один и тот же код адаптера (без ROS 2)
                                  │
            ┌─────────────────────┼──────────────────────┐
            ▼                     ▼                      ▼
   двойник MuJoCo          мост в Gazebo              железо G1
   (производитель)        (ros2_control)            (домен 0, eth)
   rt/lowcmd ⇄ rt/lowstate  /lowcmd ⇄ /lowstate      rt/lowcmd ⇄ rt/lowstate
   эталон, sim2sim         мир комплекса             перенос (фаза 7)
```

Закон привода везде один: `tau = tau_ff + kp·(q* − q) + kd·(dq* − dq)`, коэффициенты — из
контракта (ADR-0019), едут в каждой команде `LowCmd`. Где и с какой частотой его считает
каждый двойник — различается (итог этапа 0), и это измеряется, а не предполагается.

### Итог этапа 0 (13.09.2026, сессия 5)

Таблица фактов с источниками и коммитами — в журнале сессии. Что она меняет в плане:

- **0.2 → этап 3.** Слоты — раскладка 29 DoF с пустыми 13, 14, 20, 21, 27, 28 (руки с 15).
  Таблица `g1_joint_index_dds.md` неверна; тест на перестановку сверяется с мостом и MJCF,
  а не с ней.
- **0.3 → этапы 2–4.** Python-мост не заполняет `tick`, `mode_machine`, `crc` и считает
  закон привода на приход команды. C++-мост кладёт в `tick` время мира в мс, `mode_machine`
  = 4 для сцены 23 DoF и считает закон на 1 кГц. Выбор эталонного двойника определяет
  источник метки времени в адаптере, поэтому делается карточкой **до** адаптера.
- **0.5 → этап 1.** Колёс `cyclonedds` 0.10.x для Python 3.12 нет; CycloneDDS из Jazzy
  поисковик сборки обвязки не находит. Окружение выбирается после пробной установки на
  Linux, а не по чтению.
- **0.6, 0.7, 0.8** подтверждены по версиям и коду; обмен по проводу и `colcon build` —
  пробным прогоном вместе с 0.5.
- **Новое → этап 4.** URDF и MJCF производителя расходятся в пределе момента голеностопа
  (35 и 50 Н·м); только в MJCF есть демпфирование, инерция ротора и трение.
- **Новое → этап 3.** Канал SDK не отдаёт статуса сопоставления: для ADR-0016 транспорт
  создаёт читателя средствами `cyclonedds` напрямую.
- **Linux, прогон 1 (сессия 6).** 0.8, 0.6 и 0.7 подтверждены: `unitree_hg` собирается,
  SDK на `cyclonedds` 0.10.2 и 11.0.1 обменивается с ROS 2 Jazzy в обе стороны без потерь.
  `lo` не работает: у интерфейса нет мультикаста, а SDK на 0.10.2 с конфигом `lo` падает.
- **Linux, прогон 2 (сессия 6).** 0.10.2 падает при обнаружении участника 11.0.1 — робот
  на 0.10.2, так что 11.x исключён. 0.10.2 падает на блоке `<Tracing>` шаблона SDK и не
  уживается с `rclpy` в одном процессе. Пиры на `lo` работают на обеих версиях. Решение —
  ADR-0022. Этап 0 закрыт.
- **Новое → всё дальнейшее.** Вопрос «сможет ли пользователь добавить такого же робота»
  показал, что план доказывал бы только G1. Отсюда ADR-0021 и перестройка этапов 1–5.

## Этап 1. Окружение и требования пакета (Linux, затем Windows)

- **Пробный прогон на Linux** — `scripts/phase4-probe.sh` (журнал сессии 5): сборка `unitree_hg`,
  обвязка `cyclonedds` 0.10.2 на 3.12, обмен SDK ↔ ROS 2 по проводу. Выполнен дважды
  (журнал сессии 6).
- **Окружение DDS производителя** — решено, ADR-0022: C-библиотека и обвязка 0.10.2 из
  исходника, CycloneDDS 0.11+ запрещён, адаптер в процессе без `rclpy`.
- **Требования пакета робота** (ADR-0021): форма объявления рядом с кодом пакета и
  команда платформы, проверяющая их до запуска. Вендорское — SDK, `cyclonedds`,
  сообщения `unitree_hg` — объявляет пакет G1, а не `scripts/phase0.sh`.
- `scripts/phase0.sh` ставит только то, что нужно самой платформе, и по-прежнему
  сверяется с `LAUNCH_PACKAGES` и `ADAPTER_PACKAGES` (ADR-0013). Нужен ли ему
  `ros-jazzy-rmw-cyclonedds-cpp` — решается вместе с этапом 5: процессы сцены с мостом
  работают на нём.
- **Сцены Gazebo на CycloneDDS.** До прогона 1 его на машине не было: все прошлые сцены шли
  на Fast DDS. `arm6` и G1 через `ros2_control` прогнать на `rmw_cyclonedds_cpp` до моста,
  чтобы смена рантайма не смешалась с новым кодом.
- **Локальная конфигурация связи.** `lo` без мультикаста не работает; одноадресное
  обнаружение с явным пиром `127.0.0.1` работает (прогон 2) — это и есть локальная
  конфигурация (ADR-0022, пункт 5).

**Проверка:** на Linux проверка требований находит SDK и собранные сообщения; на машине
без них называет недостающее и чем его ставить.
**Карточки:** форма требований пакета — она обязана выражать и «нужен пакет», и
«запрещена версия» (ADR-0022, пункт 2).

### Ход этапа 1 (13.09.2026, сессия 8)

- **Форма требований — ADR-0025.** Значение `Requirement` из закрытого реестра видов
  (`python`, `ros2`, `executable`, `variable`), условие версии по PEP 440, «нужно» или
  «запрещено» с причиной. Объявляет **каждая сторона связи** членом своего протокола —
  `requirements` у `Twin` (закрыт пункт 8 ADR-0024) и у `ControlAdapter`: у адаптера и двойника
  разные процессы и машины, и одно объявление на пакет проверяло бы на бортовом компьютере
  дисплей для MuJoCo.
- **Команда** `env check <сценарий>`; живые `sim run` и `run` проверяют свою сторону до запуска.
  `validate` окружения не касается.
- Встроенные адаптер и двойник `ros2_control` объявляют требования выводом из того, что используют
  (`ADAPTER_PACKAGES`, `TWIN_PACKAGES`); узел запуска двойника из необъявленного пакета — ошибка
  генератора. На Windows `env check` сцены `table` называет все 12 недостающих требований.
- **Linux — `scripts/phase4-stage1.sh`:** требования на настоящей машине; сцены `arm6` и G1 через
  `ros2_control` на Fast DDS и на CycloneDDS; пиры на одной стороне (п. 3 ADR-0023) против
  шаблона C++ SDK и против собранного `unitree_mujoco`. Требования пакета G1 проверяются там
  объявлением-заменой: пакета ещё нет (этап 3).
- **Прогон 1 (сессия 9).** Требования в форме пакета G1 на настоящей машине — верно во всех шести
  случаях. Двойник `unitree_mujoco` собран и отвечает: `tick` — миллисекунды мира (фактор 1.00),
  `mode_machine` 4, команда адаптера двигает сустав. Пиры на стороне адаптера работают в обоих
  порядках запуска — но и без пиров участники 0.10.2 и двойник находят друг друга: проверка п. 3
  ADR-0023 не различает, решение не меняется. Сцены не измерены: установка платформы на Linux
  (по гипотезе) старше группы двойников, `sim run` отказал `twin.missing`.
- **Прогон 2 (сессия 10). Этап 1 закрыт.** Устаревшая установка подтверждена (`heron` 0.2.0,
  пустая группа двойников). `env check` на Linux: 0 с ROS 2, 12 недостающих без него. Сцены `arm6`
  и G1 через `ros2_control` на CycloneDDS работают, как на Fast DDS: те же числа, рантайм прочитан
  из карт процессов; мир G1 — 0.7 от реального времени. Найден и исправлен дефект: отказ адаптера
  не останавливал робота и выходил трассировкой — ADR-0026.
- Перенесено: вопрос `ros-jazzy-rmw-cyclonedds-cpp` в `phase0.sh` — вместе с этапом 5, как
  записано выше.
- **В этап 4:** робот падает между запуском двойника и первой командой — начальное условие
  объявить, а не обнаружить по позе.

## Этап 2. Общий слой (Windows)

То, что делает ADR-0021 правдой для любого робота. G1 здесь ещё не участвует.

- **Публичный API** объявлен списком модулей платформы. Тест: пакеты в
  `examples/plugins/` импортируют из платформы только их.
- **`sim run` через плагины.** Бэкенд загружается из группы `sim_backends` по
  `world.backend`; Gazebo — тем же путём. Тесты сцен Gazebo не меняются.
- **Группа двойников** в `branding` и протокол двойника: процессы как значения
  (ADR-0011), род («владеет физикой» или «мост»), требования к окружению. Конфигурацию
  связи двойник читает из `params` адаптера под бэкенд.
- **Встроенный двойник Gazebo.** Нынешнее порождение `ros2_control` для адаптера
  `ros2_control` регистрируется как двойник рода «мост». Если оно не укладывается в
  протокол, протокол неверен — это его вторая реализация.
- **Валидатор:** робот без двойника под пару «адаптер, бэкенд»; сцена из нескольких
  роботов, один из которых с двойником, владеющим физикой (ADR-0002). Коды — публичный
  API (ADR-0007), выбираются при реализации.
- **Эталонный двойник MuJoCo** — C++ или Python (итог этапа 0.3). Карточка до этапа 3:
  выбор задаёт источник метки времени в адаптере.

**Проверка (Windows):** все тесты, `arm6` и `rest_arm` проходят прежний путь без правок
профилей; ядро без `examples/` зелёное.
**Карточки:** эталонный двойник MuJoCo; форма протокола двойника — только если она
отступит от обязанностей ADR-0021.

### Ход этапа 2 (13.09.2026, сессия 7)

- **Эталонный двойник MuJoCo — ADR-0023:** C++-симулятор производителя без правок. Метка
  времени в адаптере — `tick`; двойник запускается аргументами; пиры — только на стороне
  адаптера (выведено из исходников CycloneDDS 0.10.2, **проверить прогоном на Linux до кода
  адаптера**). Вопрос этапа 4 «какой мост» закрыт.
- **Протокол двойника отступил от ADR-0021 — ADR-0024:** встроенный путь порождает элементы
  описания, файлы, узлы запуска и имена, а процессов у него нет. Общая часть — в ядре, вклад
  в сцену — протоколом бэкенда (`GazeboTwin`).
- Сделано: группа `twins`, `Ros2ControlTwin` через неё, генераторы без имени `ros2_control`,
  `sim run` через `sim_backends`, правила `twin.missing`, `twin.unloadable`,
  `twin.owns_physics_not_alone`, `PUBLIC_MODULES` с тестом. Порождённые сцены побайтно
  совпадают с прежними.
- Осталось от этапа 2: член протокола «требования к окружению» — вместе с формой требований
  этапа 1.

## Этап 3. Пакет G1: DDS-адаптер (Windows)

Дистрибутив `examples/plugins/unitree_g1/` со своим `pyproject.toml`, устроенный так,
будто его прислал производитель. Имя платформы в нём встречается только в строке группы
точек входа (раздел 17). Профиль остаётся в `examples/robots/g1_23dof/` и называет
адаптер через `plugin`.

- **Транспорт внедряется** — как ADR-0014: протокол канала DDS с двумя реализациями
  (настоящая и записывающая). Адаптер отдаёт значения, объектов SDK не строит; импорт
  SDK — внутри `connect`. Домен, участник, читатель и писатель — средствами `cyclonedds`
  по своей конфигурации (домен, интерфейс, пиры); от SDK — только IDL-типы и CRC
  (ADR-0022). Статус сопоставления различает «никто не публикует» и «не доходит» (ADR-0016).
- **Слоты ↔ суставы** по итогу 0.2: раскладка 29 DoF с пустыми слотами. Таблица — факт
  интерфейса производителя, живёт в пакете, а не в профиле. Недостающий сустав — ошибка,
  а не ноль; пустые слоты получают нулевые коэффициенты.
- **Коэффициенты** `kp`/`kd` — из контракта (ADR-0019); `tau_ff = 0`, `dq* = 0` на первом
  шаге.
- **Состояние:** `motor_state[i].q/dq/tau_est` → `RobotState` в порядке контракта; метка
  времени — по карточке эталонного двойника (этап 2), не стенные часы (ADR-0015).
- **`mode_machine`** отражается из `LowState` и сверяется с профилем при `connect`:
  «на связи не тот робот» — отказ, а не движение не тех моторов. `crc` — средствами SDK.
- **Аварийный останов:** удержание текущей позы или демпфирование (`kp = 0`, `kd > 0`).
  Решить и записать.
- **Конфигурация связи:** домен и сетевой интерфейс в `params` адаптера — единственное,
  что отличает двойник от железа.
- Добавить адаптер в `tests/test_adapter_contract.py`; тесты пакета — на записывающем
  канале, без SDK.

**Проверка (Windows):** контрактный набор и тесты пакета зелёные, тест публичного API
зелёный, ядро без `examples/` зелёное.
**Карточки:** таблица слотов; аварийный останов гуманоида; транспорт DDS.

### Ход этапа 3 (14.09.2026, сессия 12)

- **Пакет `unitree-g1` 0.1.0** в `examples/plugins/unitree_g1/`: адаптер `unitree_g1_dds` точкой входа
  группы адаптеров, из платформы — только публичный API. Тест публичного API впервые проверяет
  непустое множество пакетов.
- **Слоты и тело — ADR-0027.** Раскладка 29 приводов по именам, сверенная тестом с порядком приводов
  MJCF; `mode_machine` первого `LowState` сверяется с суставами контракта при `connect`. Попутно:
  `g1_23dof.xml` из `unitree_ros` объявляет 23 привода подряд — его порядок слотами не является.
- **Останов — ADR-0028:** демпфирование, `kp = 0`, `kd` из контракта.
- **Канал — ADR-0029:** значения на границе, `cyclonedds` напрямую, связь из `params` (`domain` и
  `interface` обязательны, `peers` по желанию), процесс с `rclpy` отвергается.
- **Общий контрактный набор** переписан на обвязки: адаптер, профиль, конфигурация связи, подача
  показаний. Проходят три адаптера. Пакет, лежащий в `examples/plugins`, но не установленный, — отказ
  сбора, а не пропуск. Каждый адаптер набора находится через свою точку входа.
- **Уточнение плана.** Имя платформы в пакете встречается не только в группе точек входа, но и в
  зависимости и импортах публичного API: без них пакет не объявит отказ (`CommandRefusedError`) и не
  прочтёт профиль.
- **Профиль G1 не менялся.** Ключ `sim.mujoco` с конфигурацией связи появится на этапе 4 вместе с
  бэкендом, которому он нужен.
- **Не проверено:** `CycloneChannel` не исполнялся ни разу; блокирующий `take_one(timeout=…)`
  обвязки 0.10.2 в прогонах не использовался. Первый прогон — этап 4.
- **В этап 5:** `run` кладёт в конфигурацию `namespace`, DDS-адаптер его не читает — топики G1
  фиксированы (`rt/lowcmd`). Это вопрос пространств имён DDS, записанный там.

## Этап 4. MuJoCo: общий бэкенд и двойник производителя (Linux)

- **`SimBackend` для `mujoco` — в платформе**, зависимость в группе `sim`: оркестратор
  процессов (ADR-0011), шаг физики из `state_rate_hz`, MJCF как вход. Протокола робота он
  не знает.
- **Двойник `unitree_mujoco`** — в пакете G1, род «владеет физикой». Сцена — файл
  `scene_23dof.xml`; конфиг производителя — Python-файл с константами, а порождать код
  ADR-0010 запрещает, так что аргументы передаются запускателю пакета. Какой мост — по
  карточке этапа 2.
- **Описание двойника — MJCF** производителя: второй вход рядом с URDF, загрузка тем же
  скриптом по закреплённому коммиту `unitree_mujoco`.
- **Сверка MJCF с профилем** — семейство правил `mjcf.*` в платформе: имена суставов,
  пределы, порядок приводов. Первое найденное расхождение — момент голеностопа 35 и
  50 Н·м (этап 0).
- Адаптер профиля: ключ `sim.mujoco`. Сценарий `examples/scenarios/humanoid_mujoco.yaml`
  с `world.backend: mujoco`.
- База: у двойника есть «эластичная лента» (п. 0.3) — решить, используется ли; помнить
  ADR-0018.

**Проверка (Linux):** `sim run` поднимает двойник, `run` выполняет `move_joints`. **Это
первое доказательство иного интерфейса.**
**Карточки:** правила `mjcf.*` (если вводятся).

## Этап 5. DDS-мост в Gazebo (Linux)

- **Двойник Gazebo в пакете G1**, род «мост»: контроллер `ros2_control` на C++ в
  ROS 2-пакете внутри `examples/plugins/unitree_g1/`. Подписан на `/lowcmd`, пишет усилие в
  интерфейсы `effort` по закону привода с коэффициентами из сообщения, публикует
  `/lowstate` (позиции, скорости, оценка момента, `tick`, `mode_machine`). Закон считается
  в `update()` — синхронно с шагом физики.
- **Генератор Gazebo** включает в сцену двойников рода «мост» через протокол ADR-0021, не
  зная их имён. Вопрос «как вендорская сторона попадает в сцену» закрыт карточкой; здесь
  — его реализация для Gazebo.
- Процессы сцены — на `rmw_cyclonedds_cpp`; домен — из конфигурации связи.
- **Пространства имён.** Платформа строит топики от идентификатора робота (`/g1/...`), а
  у робота путь фиксирован (`rt/lowcmd`). Для одного G1 — корень; для нескольких —
  DDS-домен на робота. Решить и записать.
- Интерфейсы состояния — `position`, `velocity`, `effort` (оценка момента для `LowState`).
- **Гипотеза:** мост для DDS-роботов с законом привода в команде общий и настраивается
  данными. Проверить на G1; не обобщать без второго робота.

**Проверка (Linux):** тот же `run`, та же цель, адаптер без изменений кода; меняется
только конфигурация связи.
**Карточки:** пространства имён DDS; контроллер моста.
