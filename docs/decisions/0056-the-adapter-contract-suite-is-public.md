# ADR-0056. Контрактный набор адаптера публичен, заготовка робота — пакет

**Статус:** принято; раздел 13 архитектуры, ADR-0021, критерий 10 плана фазы 5
**Дата:** 16.09.2026

## Контекст

- Требование пользователя (16.09.2026): пользователь берёт API своего робота, подключает его к платформе и
  работает с настоящим роботом **без правки ядра**. RC5 — первый, кто проходит этот путь, и доказательство
  стоит ровно столько, сколько путь доступен другим.
- Раздел 13: «каждый адаптер прогоняется через общий набор проверок». Набор — `tests/test_adapter_contract.py`:
  десять проверок протокола по обвязке `Harness` (как построить адаптер, какой профиль, как подать показания).
  Он лежит в `tests/` — вне устанавливаемого пакета. Обвязки перечислены списком `HARNESSES` в тестах
  платформы; пакет G1 попал туда правкой тестов платформы (`_vendor_harnesses`, путь к `examples/plugins`).
  У пользователя, поставившего платформу пакетом, набора нет вовсе.
- Руководство («Если производитель дал адаптер и двойник») говорит, что набор «принимает адаптер пакета через
  обвязку» — верно только для пакетов, которые платформа перечислила у себя.
- `new-robot` пишет профиль, `adapter.py` и заготовку описания. Профиль — потоковый (100 и 50 Гц, `clip`),
  адаптер подключается путём `модуль:Класс`, без пакета и без тестов. Проверка набора
  `test_is_found_through_its_entry_point` такой заготовке недоступна по построению.
- Командный класс (ADR-0049) и шкала скорости (ADR-0052) добавляют адаптеру обязанности, которые проверяются
  только набором.
- `PUBLIC_MODULES` (ADR-0021) — что пакет робота может импортировать; тест держит это для `examples/plugins`.

## Решение

**1. Набор становится модулем пакета платформы** — `testing.adapter_contract`, в `PUBLIC_MODULES`. В нём
`Harness` и класс `AdapterContract` с проверками протокола. Пакет робота подключает набор в своих тестах
наследованием и своей обвязкой:

```python
class TestMyRobotAdapter(AdapterContract):
    harness = Harness(plugin="my_robot_link", make=..., profile=..., prime=...)
```

Модуль импортирует `pytest` и ядром во время исполнения не импортируется никогда.

**2. Тесты платформы перечисляют только встроенные адаптеры.** `dummy` и `ros2_control` проходят набор тем же
наследованием. Пакет G1 прогоняет набор из своих тестов; `_vendor_harnesses` и путь к `examples/plugins` из
тестов платформы уходят. Пакет G1 переводится первым — до пакета RC: путь проверяется пакетом, который уже
был, а не только тем, ради которого путь сделан.

**3. Набор проверяет обязанности по классу связи.** Общие — как сейчас. Для `control_mode() == command`:
фаза движения не `None`; после принятой команды фаза не `idle`, пока обвязка не сообщит конец движения;
команда во время движения — `CommandRefusedError` (ADR-0049). Для всех: `supports_speed_scale` объявлен и это
`bool` (ADR-0052). `Harness` получает необязательный `finish` — «робот сообщил, что движение закончено»; у
командного адаптера без него набор отказывает с подсказкой, а не пропускает проверку.

**4. Заготовка робота — пакет.** `new-robot <имя> --control-mode streaming|command` пишет:

- `pyproject.toml` с точкой входа адаптера в группе из `branding.ENTRY_POINT_GROUPS`;
- модуль адаптера с TODO на каждую обязанность протокола и класса связи, `supports_speed_scale = False`;
- записывающую обвязку и тест, наследующий `AdapterContract`, — набор красный, пока обязанности не выполнены,
  и называет, какие;
- профиль и заготовку описания. Для `command`: `control_mode: command`, темп командного класса, рамка с
  `joint_velocity` и `joint_acceleration`, адаптеры `sim.dummy` в командном режиме и `real` пакета.

**5. Руководство получает раздел «Подключить API своего робота»** — для производителя, у которого есть только
API: заготовка → адаптер со внедряемым каналом → набор в своих тестах → `validate` → прогон на `dummy` →
`run --target real --speed-scale`. Пакет RC — живой пример этого раздела, как G1 — раздела о двойнике.

## Альтернативы

**Оставить набор в `tests/`, пакеты добавлять в `HARNESSES`.** Каждый новый робот — правка тестов платформы;
для пользователя платформы из пакета — недоступно совсем. Ровно то, что запрещает критерий 10. Отвергнуто.

**Плагин `pytest` через точку входа `pytest11`.** Набор включался бы сам у всех, кто поставил платформу, и
искал бы обвязки через ещё одну группу точек входа — седьмую точку расширения ради тестов. Наследование
делает то же явно и одной строкой. Отвергнуто.

**Команда `adapter check <плагин>`.** Проверка без `pytest` удобна, но обвязку (записывающий канал, поданные
показания) пакет всё равно пишет кодом, и её надо откуда-то найти — снова новая группа точек входа. Отложено;
модуль набора этому не мешает.

**Заготовка без пакета, как сейчас.** Адаптер `модуль:Класс` не находится по точке входа и не проходит набор,
а превращение в пакет пользователь делает сам по руководству. Первый шаг пути оказывался бы шагом в сторону.
Отвергнуто.

## Последствия

- `PUBLIC_MODULES` расширяется на `testing.adapter_contract` — обещание всем пакетам роботов (ADR-0021).
- `pytest` становится зависимостью тестов пакета робота, не ядра; группа зависимостей `testing` платформы.
- Тест «ядро не импортирует `examples/`» дополняется: тесты платформы не упоминают пакеты `examples/plugins`.
- Проверки, специфичные для `dummy`, остаются в тестах платформы: они про встроенный адаптер, не про протокол.
- Критерий 10 проверяется в CI: заготовка `new-robot --control-mode command` ставится в чистое окружение и
  проходит `validate`; её набор падает только на TODO, которые заготовка честно оставила.
