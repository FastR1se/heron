# 0013. Порождаемый запуск опирается только на объявленное окружение

Статус: принято
Дата: 2026-09-12
Уточняет: [ADR-0012](0012-observe-everything-command-the-contract.md) — механизм
для неподвижного участника сцены остаётся, но становится объявленной
зависимостью, а не предположением.

Контекст: ADR-0012 добавил в файл запуска узел `joint_state_publisher` для
робота с ролью `static`. На целевой машине пакета не оказалось, и запуск
завершился так:

```
[ERROR] [launch]: Caught exception in launch:
"package 'joint_state_publisher' not found, searching: ['/opt/ros/jazzy']"
```

Существенно не то, что пакета не было, а **как** это проявилось. Узел добавлялся
ради препятствия — второстепенной части сцены, — но отсутствие пакета убило
**всю** сцену целиком, вместе с роботом, который работал. Файл запуска не
деградирует: он либо разбирается, либо нет.

Проверить это заранее было нечем. Фаза 0 ставит явный список пакетов
(`desktop`, `ros2-control`, `ros2-controllers`, `xacro`, `robot-state-publisher`,
`rosbag2-storage-mcap`, `ros-gz`, `gz-ros2-control`), но нигде не записано, что
именно из них требуется порождаемому запуску. Два списка — что ставится и что
используется — существовали по отдельности и разошлись при первом же добавлении
узла.

Решение: **набор пакетов ROS 2, на которые может ссылаться порождаемый запуск,
объявлен в коде и совпадает с тем, что ставит фаза 0.**

Объявление живёт в генераторе запуска (`LAUNCH_PACKAGES`) и отображает имя
пакета ROS 2 на пакет, который его приносит. Совпадение проверяется тестом с
двух сторон:

- ни один `pkg` в порождённом запуске не может быть вне набора;
- каждый пакет набора обязан ставиться скриптом фазы 0.

Добавление узла из нового пакета становится тем, чем оно и является, —
изменением требований к окружению, сделанным осознанно, а не строкой, которая
работает на одной машине. `ros-jazzy-joint-state-publisher` добавлен в фазу 0
этим же решением.

Альтернативы:
(1) убрать узел и оставить препятствие с неполным деревом преобразований —
    отвергнута: это откат правильного решения из-за неправильной зависимости.
    Отрисованный наполовину робот — тот же молчаливый дефект, против которого
    написан ADR-0012, и менять один дефект на другой смысла нет;
(2) проверять наличие пакета в файле запуска и обходиться без узла, когда его
    нет — отвергнута дважды. Во-первых, XML-форма launch такого условия не
    выражает, а переход на Python-форму запрещён ADR-0010. Во-вторых, и это
    важнее, поведение, зависящее от того, что оказалось установлено, — ровно та
    молчаливая изменчивость, которую платформа существует чтобы устранять: две
    машины давали бы разные сцены из одного сценария;
(3) считать окружение целиком заданным `ros-<distro>-desktop` и не вести список —
    отвергнута: `desktop` не содержит ни `ros2-control`, ни `ros-gz`, ни
    `joint-state-publisher`, то есть фаза 0 и так ставит пакеты поимённо. Список
    существовал, просто не был связан с тем, кто его потребляет;
(4) перенести публикацию состояний неподвижного робота на системный плагин
    симулятора и мост (оба из уже гарантированного набора) — не отвергнута, но
    отложена. Механизм выглядит лучше — состояние приходит из симулятора, а не
    из значений по умолчанию, — однако он не проверен прогоном, а эта фаза уже
    трижды показала, чего стоят непроверенные механизмы. Сначала работающая
    сцена, потом улучшение.

Последствия: расхождение между окружением и порождаемым запуском стало ошибкой
теста, а не отказом на чужой машине. Список пакетов фазы 0 получил потребителя, и
теперь его нельзя сократить, не сломав проверку. Машина, где фаза 0 пройдена
раньше этого решения, требует одной команды доустановки — это цена того, что
зависимость раньше была необъявленной.
