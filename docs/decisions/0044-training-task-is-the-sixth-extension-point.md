# ADR-0044. Среда обучения выводится платформой, задача обучения — шестая точка расширения

**Статус:** принято; уточняет протокол `TrainBackend` (раздел 5), продолжает ADR-0011, ADR-0021, ADR-0024, ADR-0025
**Дата:** 16.09.2026

## Контекст

- Ядро платформы ставится в окружение обучения, ничего не заменяя (факт 0.14). `rclpy` там не импортируется.
- Isaac Lab требует поднять `AppLauncher` до импорта `isaaclab`. Процесс берёт на себя сигналы и Kit. Скрипт
  пробы завис на `simulation_app.close()`, а `train.py` выходит сам (0.11, 0.12, эксперимент 0002).
- Протокол `TrainBackend` в ядре — три метода с `Any`.
- Требование пользователя (критерий 10 плана): пользователь обучает **своего** робота под **свою** задачу без
  правки ядра. Бэкенд обучения не знает ни `arm6`, ни G1, ни задач.
- Награду пишет человек (раздел 1). Действие и наблюдение задаёт контракт (ADR-0041, ADR-0042), и задача
  менять их не должна.
- Пример `bench.yaml` объявляет `arm1` ролью `learner` в мире `dummy`, где никто не учится.

## Решение

**1. Бэкенд `isaaclab` — в ядре** (`train/`, группа `train_backends`), как `gazebo` и `mujoco` в `sim_backends`.
Isaac, torch и `rsl_rl` импортируются только в процессе обучения и в зависимости платформы не входят.

**2. Вывод среды — чистые данные, процесс — отдельно.**

- `TrainSpec` строится без Isaac: описание и закрепление базы (ADR-0048), суставы контракта, `dt =
  1/state_rate_hz`, `decimation = state_rate_hz / command_rate_hz` (нецелое — отказ
  `train.rates_not_integer`), отображение действия (ADR-0041), термы наблюдения (ADR-0042), привод (ADR-0045,
  без `kp`/`kd` — отказ `train.gains_missing`), поза отсчёта, горизонт задачи.
- Процесс — `sys.executable -m <модуль процесса бэкенда> <каталог прогона>`, и `spec.json` лежит на диске до
  запуска. Запускатель внедряется (ADR-0011), процесс — группа (ADR-0037), сухой прогон печатает команду и
  вывод.
- Процесс поднимает `AppLauncher`, собирает конфигурацию среды Isaac Lab из `spec.json` и вклада задачи,
  учит `rsl_rl` и экспортирует ONNX. Манифест и условия пишет платформа (ADR-0046).

**3. Команда `train` исполняется в окружении обучения:** `contract_id` там считает тот же код, что на стороне
исполнения. Требования бэкенда (ADR-0025): модули `isaaclab`, `isaacsim`, `rsl_rl` нужны; `rclpy` запрещён
(ADR-0003). Проверяются до запуска.

**4. Сценарий обучения.**

- `world.backend` — имя бэкенда обучения: владелец физики один (ADR-0002).
- Ровно один `learner`; соседи вне фазы — отказ `train.neighbours_unsupported`.
- У роли `learner` обязательное поле `task` — полезная нагрузка роли, как `policy` у `frozen`.
- Ученику адаптер не нужен: правило ADR-0002 об адаптере относится к миру бэкенда симуляции.
- Имя, зарегистрированное в обеих группах, — ошибка.

**5. Задача обучения — шестая точка расширения, двухслойная, как двойник (ADR-0024).**

Общая часть в ядре — `TrainTask`:

- `backend`;
- `spec: SkillSpec` — возможности, режим и `requires` будущего навыка; уходят в манифест;
- `completion` — `tolerance` и `hold_s` (ADR-0043);
- `horizon_s` — длина эпизода.

Слой бэкенда — `IsaacLabTask`, публичный модуль:

- награды, завершения эпизода и события (сброс, рандомизация) — объекты конфигурации Isaac Lab, которые модуль
  строит в процессе обучения;
- диапазон цели — данными, по суставу; командный терм цели принадлежит платформе;
- параметры агента (сеть, PPO) — по желанию, иначе умолчание бэкенда.

Платформа отдаёт задаче контекст: сущность робота с суставами контракта (`preserve_order`), имя командного
терма цели, контракт, профиль.

Не отдаёт: сцену робота, привод, частоты, менеджеры действия и наблюдения. Членов, через которые их можно
изменить, у протокола нет.

**6. Группа точек входа `train_tasks`.** Задачи `arm6` и G1 — пакеты в `examples/plugins/`, найденные той же
группой, что и сторонние. Тесты держат: ядро их не импортирует; пакет задачи импортирует из платформы только
`PUBLIC_MODULES`.

**7. `TrainBackend` уточняется значениями:** `build_env(scenario, learner)` → план; `train(план, условия)` →
каталог прогона; `export(каталог)` → артефакт. Точные подписи — этап 3.

## Проверка критерием 10

Другой робот и другая задача: профиль и URDF, пакет с `IsaacLabTask`, сценарий с `learner` и `task`, команда
`train` — ни строки ядра.

Без ядра не получится: цель не в виде позы суставов (ADR-0042), соседи в обучении, другой симулятор обучения —
для него есть точка расширения бэкенда.

## Альтернативы

**Бэкенд пакетом в `examples/plugins`.** Бэкенды симуляции лежат в ядре, а бэкенд обучения не знает роботов.
Вынос дал бы ядро, которое «умеет обучать» только с пакетом из примеров. Отвергнуто.

**Isaac внутри процесса команды.** `AppLauncher` захватывает процесс; зависание `close()` видела проба; команду
не показать до запуска и не остановить группой. Отвергнуто.

**`train.py` Isaac Lab с зарегистрированной gym-задачей.** Конфигурация — модуль Python, и из профиля её можно
получить только порождением кода, а его запрещает ADR-0010. Объекты конфигурации, собранные в процессе из
данных, — не порождение кода. Отвергнуто.

**Модуль задачи строкой `module:attr` в конфигурации прогона.** Точка расширения, не названная точкой, —
костыль. Отвергнуто.

**Задача внутри бэкенда** (награда reach в ядре). Нарушает критерий 10; задача — знание о роботе и миссии.
Отвергнуто.

**Задача в поле `task.skill` сценария.** Это поле значит «какой навык исполнить»; перегружать его — два смысла
одного поля. Отвергнуто.

**Задача возвращает целую `ManagerBasedRLEnvCfg`.** Сможет менять действие и наблюдение — ровно то, что обязано
прийти из контракта. Отвергнуто.

## Последствия

- Раздел 5 архитектуры — шесть точек расширения; группа `train_tasks` в `branding`.
- `bench.yaml`: `arm1` получает роль `scripted` — `learner` без `task` станет ошибкой разбора.
- Заготовка модуля задачи командой CLI (этап 3), раздел руководства «обучить своего робота» (этап 8).
- Не проверено: что среда Isaac Lab собирается объектом конфигурации без регистрации gym-задачи
  (`ManagerBasedRLEnv(cfg)` напрямую) и принимается `RslRlVecEnvWrapper`. Это факт до кода этапа 3.
