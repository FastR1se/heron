# 2026-09-18 (сессия 24)

## Задача
Записать пошаговую инструкцию «как вывести команды на настоящего Unitree G1 через платформу» —
по просьбе пользователя, с упором на зависимости: на них он спотыкается каждый раз.

## Сделано
- `docs/g1-on-hardware.md`: три части и таблица ошибок. Зависимости — сборка C-библиотеки CycloneDDS
  0.10.2 из исходника, обвязка против неё, SDK производителя на закреплённом коммите, платформа и
  пакет G1 в отдельный venv; настройка — интерфейс, блок `real` в профиле, сцена в мире `dummy`;
  робот — безопасность, первое подключение без команд, запуск. В конце — порядок решений `run` от
  валидатора до сторожевого таймера.
- Команды не выдуманы: сняты со `scripts/phase4-probe.sh` (шаг 0.5: `cmake` с флагами,
  `CYCLONEDDS_HOME=… pip install cyclonedds==0.10.2`, коммит SDK `65691c8`) и
  `scripts/phase4-stage4.sh` (шаг env: `pip install pydantic pyyaml typer packaging`, затем
  `--no-deps -e` платформы и пакета).
- Путь проверен сухим прогоном: временная копия профиля G1 с ключом `real`, сцена в мире `dummy`,
  `validate` — 0 ошибок, `run --target real --speed-scale 1 --dry-run` — план «мир —
  действительность». Временные файлы удалены.
- Ссылки на документ из руководства: раздел 19 (G1 в симуляторах), рецепт 23 (API своего робота и
  железо), таблица «Что читать дальше». Якоря и относительные ссылки обоих документов проверены
  скриптом.
- Кода платформы не менял; тесты не запускались.

## Проблемы и тупики

**Сухой прогон не ловит недопустимую шкалу скорости.** `run --target real --speed-scale 0.3
--dry-run` печатает план и выходит с кодом 0, хотя настоящий прогон будет отменён: G1 объявляет
`supports_speed_scale = False`. Причина — порядок в `cli/run.py`: `refuse_undeclared_scale`
вызывается **после** возврата из сухого прогона, вместе с созданием адаптера. Проверено прямо на
классе: `refuse_undeclared_scale('unitree_g1_dds', G1DdsAdapter, 0.3)` бросает `RunError`.
Исправлять не стал — правка поведения CLI, а сессия была про документ; предупреждение записано в
инструкцию и названо пользователю. Кандидат в отдельную правку: объявление шкалы читается с класса
и не требует ни подключения, ни окружения, поэтому проверку можно поднять до ветки `dry_run`.

**`rclpy` не запрещён адаптером формально.** ADR-0022 требует, чтобы процесс DDS-адаптера не
загружал `rclpy`, но в `REQUIREMENTS` пакета G1 только три пункта: `cyclonedds == 0.10.2`, запрет
`>= 0.11` и `unitree_sdk2py`. То есть подключённый ROS 2 в терминале робота платформа не заметит.
В инструкции это написано как правило окружения, а не как проверка.

**Профиль G1 не содержит ключа `real`** — только `sim.dummy`, `sim.gazebo`, `sim.mujoco`. Значит,
«вывести на железо» начинается с правки профиля, и инструкция обязана это называть первым делом,
иначе `run --target real` отвечает «нет адаптера 'real'». В репозиторий блок не добавлял: домен и
интерфейс — свойства конкретной машины и сети.

## Наблюдения
- Все вопросы пользователя про зависимости сводятся к трём причинам: нет колёс CycloneDDS 0.10.2,
  версия 0.11 запрещена, платформы нет в PyPI. Инструкция начинается с этих трёх фактов — без них
  флаги `--no-deps` и `CYCLONEDDS_HOME` выглядят произволом.
- Самый безопасный первый контакт с роботом — `connect` + `read_state`: он ждёт `LowState`, сверяет
  `mode_machine` и не отправляет ни одной команды. У CLI такой команды нет, поэтому в инструкции —
  скрипт на семь строк. Возможный кандидат: `heron link check <сценарий>`.

## Дальше
Работа по плану — **этап 3 фазы 5** (пакет RC5), новая сессия. Открытое: поднять проверку шкалы
скорости в сухой прогон; решить судьбу версии `heron` в зависимостях `arm6_reach`.

## Сделано
- Создан скрипт обнаружения `/home/user/g1/discover_mode6.py`: подписывается на `rt/lowstate`

- Попытка запуска: робот недоступен по сети (ping не проходит). Скрипт ждёт 30 с и выходит.

## Проблемы и тупики
- Робот не в сети: не пингуется с машины пользователя. Невозможно получить `LowState` без
  сетевого доступа.
- Возможные причины: робот выключен, не в режиме low-level, другой IP/подсеть, Wi-Fi не

- Ошибка `BodyMismatchError: mode_machine = 6` подтверждает: железо может возвращать
  значения, которых нет в MJCF-двойнике (в коде комментарий: «What the hardware reports is not

- 23 DoF в профиле ≠ 23 DoF в железе: `mode_machine` — это enum прошивки, а не количество
  суставов в URDF.

## Дальше

2. Запустить скрипт обнаружения — он покажет точный набор активных слотов.

   (journal 2026-09-18, session 25)».

2. **Создан профиль `g1_27dof`** (`examples/robots/g1_27dof/profile.yaml`):
   - `joint_order` — 27 суставов в порядке discovery-скрипта

   - Адаптер `real` с `domain: 0, interface: wlp2s0`

6. **Сухой прогон** — успешен: контракт `ddd36a5fdace0265 revision 1`, связь `real ->

## Проблемы и тупики
- Вендор не поставляет 27-DoF описание: использовали 29-DoF lock_waist URDF и 29-DoF MJCF.
  Валидатор правильно сообщает `urdf.name_differs` и `mjcf.differs_from_urdf` (ankle

- Лимиты wrist_pitch/yaw в URDF/MJCF — `[-1.61443, 1.61443]`, ужеже чем у shoulder
  pitch `[-3.0892, 2.6704]`. Профиль приведён к моделям (ошибки `position_limit_wider`
  исправлены).
- Массивы лимитов пришлось пересчитать вручную: 27 значений в точном порядке
  `joint_order`. Ошибка длины (`limits.length_mismatch`) на первом заходе — 29 вместо 27.

## Наблюдения
- `mode_machine` — enum прошивки, не количество DoF в URDF. Железо может возвращать
  значения, которых нет в MJCF-двойнике (код предупреждал: «added as a fact when it is
  one (phase 7), not guessed»).
- 27-DoF = 29-DoF wrists + 23-DoF waist (только yaw). Это новый факт для фазы 7.

# 2026-09-18 (сессия 28)

## Задача
Исправить «трескание» суставов на реальном G1 при первом запуске `move_joints`. Симуляция
работала, железа нет — корень: высокие `kp` на мелких моторах + неизвестная стартовая поза.

## Сделано
1. **Понижены gains в профиле `g1_27dof`** (`examples/robots/g1_27dof/profile.yaml`):
   - Ноги: `kp` 60/100 → 80/120, `kd` 1/2 → 2/4 (больше момента для удержания)
   - Плечи/локти: `kp` 40 → 30, `kd` 1 (умножено на 0.75)
   - Запястья (pitch/yaw): `kp` 40 → **15**, `kd` 1 (умножено на 0.375)
   - Contract `revision` → 1 (хеш обновился: `ac6a9f84de528dca`)

2. **Увеличен `duration` в сценарии** (`~/g1/g1_real.yaml`): 8.0 → **20.0 с**

3. **Валидация** — 0 ошибок, 3 ожидаемых предупреждения.

4. **Тесты адаптера** — все 25 проходят.

## Причина «трескания»
| Симуляция | Реальность |
|-----------|------------|
| Старт в нуле | Робот включается в произвольной позе (руки висят, ноги согнуты) |
| Идеальная физика | Трение, люфты, гравитация |
| Малый delta позиции | Большой delta → большая ошибка → `tau = kp * error` |
| `kp=40` на wrist OK | `kp=40` на wrist → 40×2рад ≈ 80 Нм → перегрузка мелкого мотора |

## Наблюдения
- `move_joints` делает **линейную интерполяцию позиции** без ограничения скорости/ускорения
- На железе **первый тик** определяет `start_pose` из реального состояния (ADR-0032)
- Если `start_pose` далеко от `target` → большая скорость → большие моменты
- Решение: снизить `kp` на слабых моторах + увеличить длительность
