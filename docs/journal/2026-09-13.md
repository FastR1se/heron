# 2026-09-13

## Задача
Фаза 4, первый шаг: вендорский робот — Unitree G1 в модификации на 23 степени
свободы — через собственный путь платформы (профиль → валидатор → генераторы
Gazebo → `ros2_control`), без MuJoCo и без правок ядра под робота. Где нативно не
выходит — предложить варианты.

## Сделано
- Сверены с исходниками производителя внешние факты: `g1_23dof.urdf` в
  `unitree_ros`, двойник `unitree_mujoco` и его мост (`rt/lowcmd`, `rt/lowstate`,
  без контроллера баланса), канал `rt/arm_sdk` для уровня `partial` на железе.
- `examples/robots/g1_23dof/`: профиль (23 сустава, `low`, скорости сужены до
  3 рад/с) и скрипт загрузки описания по закреплённому коммиту
  `7d6075f7f58588b189b940130e3edab3c839b2df` частичным клонированием. Описание
  (110 МБ, 167 мешей) в git не попадает.
- ADR-0017 — порождённая копия описания ссылается на меши абсолютными
  `file://`; разрешение ссылки одно на валидатор и генератор
  (`core.urdf.resolve_mesh`).
- ADR-0018 — свободную базу платформа не закрепляет; новое правило
  `urdf.free_base_uncontrolled` объявляет это условием прогона.
- Сценарий `examples/scenarios/humanoid.yaml` с задачей `move_joints` на 23
  сустава; `sim run --dry-run` и `run --dry-run` строятся.
- Контракт G1 зафиксирован (`2234ef1227ad52f4`).
- CI: загрузка описания в задаче тестов; проверка, порождение, `--check` и оба
  сухих прогона G1 в задаче без вендорских зависимостей.
- README и руководство по добавлению робота: состояние фазы, три новых «частых
  отказа».
- 299 тестов (было 287), ruff и mypy чисты.

## Проблемы и тупики

**План из прошлой сессии не закрывает фазу.** Сессия 14 записала кандидата: G1 в
Gazebo с фиксированной базой, «ядро не правится ни строкой — это и есть тезис
фазы». Перечитав раздел 14 и таблицу раздела 9, я увидел, что тезис подменён.
Фаза 4 требует **принципиально иного интерфейса**, а через `ros2_control` G1
говорит ровно тем же адаптером, что `arm6`. Этот путь доказывает инварианты 5 и 7
на роботе вчетверо больше, но не абстракцию связи. Раздел 9 прямо называет второй
класс: «вендорский DDS-SDK, гуманоид, свой транспорт». Пользователь выбрал сначала
нативный путь; это разумный первый шаг, но **фаза 4 им не закрывается**, и это
записано здесь, чтобы не закрыть её по привычке.

**Пересказ чужого файла оказался ненадёжен.** Внешние файлы я читал через
инструмент, отвечающий пересказом. На вопрос о числе приводов в `g1_23dof.xml` он
дважды ответил противоречиво: «23 привода» и тут же список из 29 имён. Проверить
это изнутри сессии не удалось. Пределы суставов для профиля я взял из такого же
пересказа — и поэтому не доверял им, а отдал сверку валидатору на настоящем файле.
Все 23 предела сошлись. Это первый случай, когда валидатор проверил не
пользователя, а меня.

**Две таблицы производителя расходятся.** По таблице индексов DDS для 23-степенной
версии руки — это слоты 13–22; пример `g1_arm5_sdk_dds_example.py` адресует руки
слотами 15–28 раскладки на 29 степеней. Для текущего шага это неважно: через
`ros2_control` суставы идут по именам. Но это ровно та величина, описанная у
производителя дважды, которую DDS-адаптер будет обязан сверять, а не угадывать.

**Предупреждение, которое было право.** Первый прогон валидатора на G1 дал одно
предупреждение: `urdf.name_differs` — описание называет робота `g1_23dof`,
профиль `g1`. Первая реакция — «ожидаемо, у производителя своё имя». Остановил
журнал сессии 9: предупреждение, объявленное ожидаемым, перестаёт читаться. На
деле оно указывало на настоящую неоднозначность: у производителя два десятка
описаний G1, и имя `g1` не говорит, какое из них профиль описывает. Профиль
переименован в `g1_23dof`, предупреждение исчезло, потому что было устранено, а не
принято.

**Дефект, спавший с фазы 2.** Валидатор проверял меши относительно входного
описания и был прав. Генератор писал копию в другой каталог, а Gazebo и RViz
получают её строкой без каталога — относительная ссылка разрешается ни от чего.
`arm6` мешей не имел, и дефект три фазы не проявлялся. Форма та же, что у всех
отказов фазы 2: артефакт корректен, потребитель читает иначе. Разница в том, что
этот найден до прогона — чтением порождённого файла глазами потребителя, а не по
логам.

**Свободная база.** Робот с `low` и без сустава к миру в Gazebo не стоит. Закрепить
его нечем без нового поля схемы или без авторства кинематики (ADR-0009).
Пользователь выбрал «честно»: не закреплять, а объявить. Рассматривал ошибку
вместо предупреждения — отказался: стенд, подвес, устойчивое шасси делают такую
конфигурацию законной, и валидатор, запрещающий исправного робота, приучает
пропускать проверку.

**Два места для lock-файла.** `ProfileSource.lock` читает lock из корня реестра,
а `validate` и `contract lock` — из каталога файла профиля. Для профиля вида
`<корень>/<имя>.yaml` это одно место, для `<корень>/<имя>/profile.yaml` — два
разных. Сейчас ничего не ломается: `ProfileSource.lock` нигде не вызывается. Но это
величина, описанная дважды, и первый же её потребитель выберет одно из двух мест
наугад. Не чинил — записал.

**Мелочь.** `gh` на машине разработки не установлен; хеш коммита производителя
взят через API GitHub.

## Наблюдения
- Ядро не правилось под робота ни строкой, но правилось дважды ради всех роботов:
  разрешение мешей и правило свободной базы. Инвариант 5 держится, а вендорский
  робот оказался лучшей проверкой ядра, чем опорные примеры, написанные под него.
- В `urdf.free_base_uncontrolled` нет слова «гуманоид» (инвариант 7): оно говорит
  об уровне доступа и о звене `world`. Похоже, «тип робота» почти всегда
  раскладывается на пару объявленных фактов из разных источников.
- Описание производителя несёт тег `<mujoco>` и закомментированный плавающий
  сустав «раскомментировать при конвертации в MuJoCo». Один файл обслуживает два
  симулятора правкой комментария — то, от чего платформа избавляет, у
  производителя живёт вручную.
- Двойник MuJoCo от производителя не содержит контроллера баланса. Значит,
  уровень `partial` в симуляции производителя недостижим вовсе, и на этом месте
  абстракция уровней доступа ещё будет проверена.

## Дальше
Прогон на Linux-машине:

```
git pull
python examples/robots/g1_23dof/fetch_description.py
heron sim run examples/scenarios/humanoid.yaml --into generated/humanoid -R examples/robots
heron run examples/scenarios/humanoid.yaml -R examples/robots
```

Вероятные места отказа, по порядку: загрузка `file://`-мешей Gazebo и RViz; тег
`<mujoco>` в описании; предупреждение KDL об инерции корневого звена `pelvis`;
23 контроллера на 500 Гц в реальном времени; робот, падающий до активации
контроллеров. Ожидаемый результат — движение рук лежащего робота; снять гифку.

После прогона — вернуться к критерию фазы 4: иной интерфейс (DDS SDK) и двойник
MuJoCo. Открытые вопросы оттуда: уровень `partial` без контроллера баланса в
двойнике, расхождение таблиц индексов производителя, конфликт питоновского
CycloneDDS с CycloneDDS из ROS 2 в одном окружении.
