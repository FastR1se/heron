- `joint_state_broadcaster` spawner умирал после успешной активации

## Сделано
1. **Проанализировал логи и сгенерированные файлы** в `/home/user/heron/generated/jena/`
2. **Нашёл причину:** `controllers.yaml` и URDF `ros2_control` объявляли только `state_interface: position`, но `joint_trajectory_controller` требует `velocity` (и `effort`) для интерполяции траектории.
3. **Исправил `src/heron/ros2/names.py`:** функция `state_interfaces()` теперь возвращает все 3 интерфейса (`position`, `velocity`, `effort`) когда используется trajectory controller (`control_mode: command` или есть gains).
4. **Обновил тесты** под новое ожидаемое поведение.
5. **Проверил на запущенном симуляторе:**
   - Перегенерировал сцену → `controllers.yaml` и URDF теперь содержат все 3 state interface
   - `joint_trajectory_controller` активируется успешно (статус `active`)
   - Ручная отправка `JointTrajectory` движет робота в целевую позу `[0.0, -1.0, 0.2, 0.0]`
   - Все тесты проходят (кроме pre-existing onnx failures)

## Проблемы и тупики
- **`goto_joints` skill не работает через `heron run`** — адаптер `Ros2ControlAdapter` не читает `/joint_trajectory_controller/controller_state` для определения `MotionPhase` (IDLE/MOVING/HALTED). Навык требует фазу движения, адаптер возвращает `motion=None`.
- **Velocity/effort в `/joint_states` — NaN** — плагин `gz_ros2_control` в Gazebo не публикует их по умолчанию, даже если они объявлены в URDF. Это косметическая проблема, управление работает.
- **Spawner `joint_state_broadcaster` умирал после успешной активации** — известная особенность spawner'а: сервис `switch_controller` отвечает медленно, spawner ретраится, контроллер уже активен → "already active" → spawner умирает. Не блокирует работу.

## Наблюдения
- Корневая проблема была в несоответствии между тем, что генерирует платформа (только position state interface), и тем, что требует `joint_trajectory_controller` (position + velocity + effort).
- Исправление в `names.py` каскадно обновило и `controllers.yaml`, и URDF `ros2_control` блок — единая точка правды сработала.
- Адаптеру не хватает подписки на `controller_state` топик для командного класса навыков.

## Дальше

2. (Опционально) Настроить `gz_ros2_control` для публикации velocity/effort.

## Проблемы и тупики

**Мой вывод о `poll` был ошибочен.** В первом разборе я сказал пользователю, что после правки

исходника до утверждения сэкономила бы ложное замечание. Нашлось при попытке исправить мнимый дефект.

## Проблемы и тупики

**Лимит API трижды обрывал агентов.** Две рабочие копии исчезли вместе с ветками (в них ещё не было
записанных файлов), агенты пересоздали их. Урок: коммитить в ветке агента раньше, а не одним коммитом в
конце.

**Диск C.** Два первых прогона pytest агента RC писали `tmp_path` в `%TEMP%` на C, пока правило не было
передано явно: `TMP`, `TEMP`, `--basetemp` и кэши — на D. В `%TEMP%\pytest-of-LEGION` остались три
каталога (4.7 МБ), чьи — не определить, не удалены. Служебные файлы самого ассистента (журналы фоновых
задач) по-прежнему на C.

**Две дыры ядра нашлись только пакетом RC — тем, что проверка не могла провалиться.** Критерий 3 фазы 5
(«validate отклоняет потоковый навык на RC5») без правки ядра был невыполним: `check_profile` не вызывал
`check_skill_against_profile`, и тест на это не мог упасть, потому что его не было. Первая правка
валидатора упала на цикле импорта (`skills.library` → `skills.learned` → `validator`), поэтому библиотека
разрешается внутри правила. `env check` отвечал только за мир сценария, и скрипт стенда повторял
требования адаптера вручную — дублирование величины, от которого правило «один раз» и защищает.

**Отвергнутое в фазе 8** (подробно — в карточках): исполнители роботов потоками в процессе координатора
(G1 отвергает процесс с `rclpy`, ADR-0022); каналы stdin/stdout (координатор знал бы окружение каждого
робота); подключение робота до ответа координатора (процесс чужого прогона тронул бы робота — добавлен
`welcome`/`rejected`); «пробный старт» навыка для проверки цели (костыль: `start()` стороннего навыка
может послать команду). Зависание 10 с на робота на Windows: `socket.makefile` не будил читателя при
закрытии из другого потока — чтение прямо из сокета.

**Отвергнутое в части G1:** флаг `mounted` в `params` (вторая запись одной величины), уровень `partial`
в симуляции (встроенного контроллера нет), адаптер, читающий описание (правка ядра); тело производителя
`g1_dual_arm` (значение 9 никто не сообщал). `phase6-arm6-gains.py` для G1 неприменим (9^14 комбинаций) —
новый скрипт обходит поддерево выборкой с зерном. В `phase6-stage5.sh` проверка «одна строка» отбрасывала
строки YAML-списка и дала бы 0 на Linux — исправлено.

**RC: расхождения SDK с документацией** — в плане фазы 5 (0.50–0.57): открытого чтения RTD нет; маркеры
пакета проверяются один раз; несовпадение версий — только предупреждение; обработчика подтверждения по
умолчанию нет; неудачный `get_robot_info` возвращает правдоподобное `rc10` с нулевыми DH; предел 3.14
рад/с, а не π.

**Heredoc в Git Bash** снова испортил правку скрипта; применено файлом-скриптом.
