# Как добавить своего робота

От модели робота до сцены в симуляторе. Правок в ядре не требуется ни на одном
шаге: профиль — данные, а не код (инвариант 5).

## Что нужно иметь

Три вещи, и только первая имеет отношение к трёхмерной модели.

| | Что это | Откуда берётся |
|---|---|---|
| **Описание кинематики** | `.urdf`: дерево звеньев и сочленений, оси, пределы, массы, инерции, меши | пакет производителя, экспорт из CAD или руками |
| **Профиль** | `.yaml`: контракт представления данных, возможности, лимиты, адаптеры | пишете вы, по паспорту робота |
| **Адаптер** | связь с конкретной машиной | для Gazebo готовый `ros2_control`, для железа — свой плагин |

Для симуляции достаточно первых двух: адаптер симулятора уже есть.

## Шаг 1. Описание кинематики

### Почему CAD-модели недостаточно

Это главный источник недоразумений, поэтому сразу.

CAD-сборка — SolidWorks, Fusion, STEP — знает **тела и сопряжения**. Она не
знает того, без чего робот не робот:

- какое сопряжение является **приводом**, а какое просто контакт двух деталей;
- **предел хода** привода, его максимальная скорость и момент;
- что считать **базой**, а что инструментом;
- направление и знак каждой оси.

Это не геометрия, а паспортные данные привода. Поэтому «загрузить CAD» — всегда
**экспорт с ручным довводом**, а не импорт файла. Экспортёр показывает вам
сборку и спрашивает: вот это сочленение — привод? вокруг какой оси? в каких
пределах?

### Путь а: готовый пакет производителя (предпочтительный)

У большинства серийных роботов есть публичный ROS-пакет с описанием — UR,
Franka, Kinova, xArm, Unitree и другие. Тогда CAD не нужен вовсе: берёте
`.urdf` или `.urdf.xacro` из пакета, и он уже содержит выверенные инерции,
пределы и меши.

### Путь б: экспорт из CAD

| Система | Инструмент |
|---|---|
| SolidWorks | `sw2urdf` — размечаете оси и сочленения прямо в сборке |
| Onshape | `onshape-to-robot` |
| Fusion 360 | `fusion2urdf` |
| Blender | Phobos |

Все они живут вне платформы: она читает результат, а не вызывает экспортёр.

### Путь в: руками

Оправдан, когда геометрия простая и меши не нужны — стенд, захват, препятствие.
Пример такого описания: [`examples/robots/urdf/arm6.urdf`](../examples/robots/urdf/arm6.urdf),
шесть степеней свободы на цилиндрах и параллелепипедах, без единого внешнего
файла.

### Шаблоны xacro

Если файл — `.urdf.xacro`, разверните его один раз в окружении ROS 2:

```bash
xacro robot.urdf.xacro > robot.urdf
```

Платформа шаблоны не разворачивает намеренно ([ADR-0009](decisions/0009-generators-do-not-author-kinematics.md)):
для этого нужен инструментарий ROS 2, а притвориться, что шаблон разобран,
означало бы превратить всю последующую сверку в проверку, которая молча ничего
не делает. Поэтому нерасширенный шаблон даёт предупреждение `urdf.not_rendered`,
а не тишину.

### Требования к описанию

Список короткий, и каждый пункт — причина, по которой робот не появляется в
симуляторе:

- **одно корневое звено.** Робот — дерево с одним корнем; иначе непонятно, за
  что его держать в мире. Проверяется как `urdf.no_root_link`;
- **`<inertial>` с ненулевой массой и невырожденным тензором у каждого звена.**
  Звено с нулевой массой Gazebo молча выбрасывает вместе со всем поддеревом —
  самая частая причина невидимого робота;
- **`<collision>`** у всего, что должно сталкиваться;
- **`<limit>`** у каждого `revolute` и `prismatic`;
- **разрешимые пути к мешам.** Относительные пути платформа проверяет сама;
  `package://` требует, чтобы пакет лежал в `GZ_SIM_RESOURCE_PATH`, и такие
  ссылки платформа проверить не может — она честно предупреждает
  (`urdf.mesh_unresolvable`), а не делает вид, что проверила.

Описание — **вход** платформы. Она его читает и сверяет, но никогда не
переписывает. Генераторы вклеивают в **копию** блок управления, оставляя ваш
файл нетронутым.

## Шаг 2. Заготовка

```bash
heron profile new my_robot --into examples/robots                         # поток команд
heron profile new my_robot --into examples/robots --control-mode command  # «выполни движение»
```

```
examples/robots/my_robot/
├── profile.yaml                    # данные: контракт, возможности, лимиты, адаптеры
├── pyproject.toml                  # пакет: точка входа адаптера, группа test
├── src/my_robot/adapter.py         # скелет ControlAdapter: все методы протокола и обязанности класса — TODO
├── src/my_robot/testing.py         # обвязка: адаптер на записывающем канале, показания робота
├── tests/test_my_robot_adapter.py  # общий контрактный набор платформы, наследованием
└── urdf/my_robot.urdf              # скелет описания — дальше это ваш входной файл
```

Адаптер сразу пакет: иначе платформа его не найдёт — у неё нет частного пути ни к
одному адаптеру ([ADR-0056](decisions/0056-the-adapter-contract-suite-is-public.md)).
Поставьте пакет и прогоните набор — он красный, пока TODO не сделаны, и каждая
неудача называет свой:

```bash
pip install -e examples/robots/my_robot[test]
pytest examples/robots/my_robot/tests
```

Если SDK производителя не ставится обычным `pip install` (архив, сборка из исходника, свой venv),
положите рядом с `pyproject.toml` пакета `install.sh`: платформенный `scripts/install.sh` найдёт его
и запустит, а окружение ляжет в `~/robot-stack/<пакет>`
([ADR-0071](decisions/0071-one-installer-packages-install-themselves.md)). Образец — установщик пакета
RC, [examples/plugins/robopro_rc/install.sh](../examples/plugins/robopro_rc/install.sh). Установщик
ищется в `examples/plugins/*/`, поэтому такой пакет кладут туда.

Скелет описания — стартовый **вход**, а не выход генератора: платформа его
больше никогда не перезапишет. Замените его своим файлом (или подставьте путь к
нему в `description.urdf`) и правьте профиль под него.

Число суставов в заготовке задаётся: `--dof 7`.

## Шаг 3. Профиль

### Контракт

Сердце профиля. Это соглашение о том, **как представлены данные**, которыми
платформа обменивается с роботом.

```yaml
contract:
  revision: 1
  joint_order: [joint0, joint1, joint2, joint3, joint4, joint5]
  angle_unit: rad          # rad | deg
  state_rate_hz: 100       # как часто робот отдаёт состояние
  command_rate_hz: 50      # как часто принимает команду
  observation:
    - {type: joint_pos, scale: 1.0}
    - {type: joint_vel, scale: 0.05}
  action:
    type: joint_position
    clip: [-1.0, 1.0]
```

**`joint_order` — не список суставов робота, а вектор, которым платформа
командует.** Суставы, которыми управляет встроенный контроллер или отдельный
канал (пальцы захвата, например), сюда не входят. Имена обязаны совпадать с
именами в описании — за этим следит валидатор.

Порядок нормативен: перестановка двух элементов меняет смысл всех данных и
идентификатор контракта.

Каждое поле контракта во что-то превращается при порождении сред:

| Поле | Во что превращается |
|---|---|
| `action.type` | командный интерфейс `ros2_control`: `position`, `velocity`, `effort` |
| `observation` | интерфейсы состояния — и ничего сверх объявленного |
| `joint_order` | состав и порядок суставов контроллера |
| `state_rate_hz` | частота `controller_manager` и шаг физики мира |
| `angle_unit` | перевод при сверке с описанием (URDF всегда в радианах) |

Допустимые термы наблюдения: `joint_pos`, `joint_vel`, `joint_torque`,
`base_lin_vel`, `base_ang_vel`, `base_orientation`, `previous_action`. Термы про
базу и предыдущее действие в интерфейсы суставов не превращаются — они приходят
из одометрии и от того, кто произвёл действие.

Типы действия: `joint_position`, `joint_velocity`, `joint_torque`,
`base_velocity`, `cartesian_pose`, `gripper_width`. Три последних не
отображаются на интерфейс сустава, и генератор их **отклоняет**, а не
приближает: робот, который двигается и при этом неправ, — ровно тот отказ, ради
которого платформа написана.

### Возможности

Чем робот умеет быть полезен. Реестр закрыт:

```
base.velocity   base.pose   arm.joint_position   arm.joint_torque
arm.cartesian   gripper.binary   gripper.width   whole_body.torque
```

Возможность — ровно два сегмента `<домен>.<аспект>` и **никаких параметров
внутри** ([ADR-0001](decisions/0001-capability-format.md)). Сколько степеней
свободы и в каких диапазонах — уже сказано в контракте и лимитах, и второй
источник правды для тех же величин был бы ровно тем классом ошибок, ради
которого платформа существует.

Нужного ключа нет в реестре — объявляйте свой в домене `x_`:
`x_myvendor.dance_mode`. Ядро о нём ничего не знает и знать не должно.

### Режим управления

```yaml
control_mode: streaming    # или command
```

- `streaming` — робот принимает **поток команд** на фиксированной частоте
  (`ros2_control`, вендорский DDS-SDK). Обученные политики работают только так.
- `command` — робот принимает «выполни это движение» и сообщает о завершении
  (сетевой API). Политика с циклом 50 Гц здесь неисполнима, и валидатор
  отклонит такой навык до запуска. Навык этого класса — `goto_joints`: одна
  команда-цель и допуск прибытия; фазу движения (`idle`, `moving`, `halted`)
  сообщает адаптер ([ADR-0049](decisions/0049-command-class-skill-and-motion-phase.md)).

Режимы сравниваются равенством, в обе стороны: `goto_joints` на потоковом роботе
так же отклоняется, как `move_joints` на командном.

Отсюда же выбирается класс контроллера: `streaming` даёт групповой контроллер,
`command` — траекторный.

### Лимиты

```yaml
limits:
  joint_position: {min: [...], max: [...]}    # длина = число суставов контракта
  joint_velocity: {max: [...]}
  joint_acceleration: {max: [...]}             # командный класс: по нему контроллер строит движение
  cartesian_velocity_max: 0.25
  gripper_width_max: 0.08
```

**Лимиты профиля — предохранительная рамка, а не паспорт.** Они обязаны быть
**уже** пределов модели: сузить можно и нужно, расширить нельзя. Профиль,
разрешающий больше, чем физически может модель, — ошибка валидатора
(`urdf.position_limit_wider`).

Единицы — те, что объявлены в `angle_unit`. Если контракт в градусах, лимиты
тоже в градусах; при сверке с описанием платформа переведёт сама.

Прогон на железе (`run --target real`) без `joint_position` или `joint_velocity`
не начнётся — `real.limits_missing`
([ADR-0051](decisions/0051-a-real-run-is-chosen-by-target.md)). Шкала скорости
прогона обязательна там же: `--speed-scale 0.1`
([ADR-0052](decisions/0052-speed-scale-is-a-run-quantity.md),
[ADR-0057](decisions/0057-speed-scale-squares-the-acceleration.md)).

### Адаптеры

```yaml
adapters:
  sim.gazebo:
    plugin: ros2_control
  sim.dummy:
    plugin: dummy
  real:
    plugin: my_robot                    # точка входа пакета из заготовки
    params: {host: "http://10.10.10.20:8081"}
```

Ключ — либо `real`, либо `sim.<бэкенд>`. Сцена объявляет ровно одного владельца
физики, и робот без адаптера под этот бэкенд в неё не попадёт
([ADR-0002](decisions/0002-single-physics-authority.md)).

`plugin` — либо имя точки входа установленного пакета, либо путь
`модуль:Класс` для плагина, который лежит на машине, но ещё не упакован. Заготовка
пишет первое: её адаптер — пакет с точкой входа.

**Инвариант 3 живёт здесь:** между симуляцией и железом меняется только этот
блок. Тот же образ, тот же навык, та же миссия.

## Шаг 4. Проверка

```bash
heron validate examples/robots/my_robot/profile.yaml
```

Коды возврата: `0` — чисто, `1` — найдены ошибки, `2` — вход не читается.

Сверка профиля с описанием — то, ради чего описание остаётся входом. Профиль и
URDF рассказывают об одном роботе двумя способами, написаны в разное время и,
как правило, разными людьми; каждое расхождение между ними платформа ловит до
запуска.

| Код | Что значит | Что делать |
|---|---|---|
| `urdf.file_not_found` | путь из `description.urdf` не разрешился | путь читается **от файла профиля**, а не от рабочего каталога |
| `urdf.joint_missing` | сустав контракта отсутствует в описании | сустав переименовали в модели — перенесите имя в `joint_order` |
| `urdf.joint_not_commandable` | контракт командует суставом, который модель объявила `fixed` | либо убрать из `joint_order`, либо сделать сустав подвижным |
| `urdf.position_limit_wider` | профиль разрешает больше физического предела | сузить лимиты профиля |
| `urdf.velocity_limit_wider` | то же по скорости | то же |
| `urdf.no_root_link` | нет единственного корневого звена | дерево разомкнуто или замкнуто в цикл |
| `urdf.mesh_not_found` | ссылка на несуществующий меш | путь читается от описания, а при заданном `mesh_dir` — от него |
| `urdf.collision_mesh_heavy` | *(предупреждение)* меш столкновений крупнее 1000 треугольников | в `<collision>` ставят примитив по габариту звена; `<visual>` остаётся как есть |
| `urdf.joint_not_in_contract` | *(предупреждение)* подвижный сустав описания платформе неизвестен | ожидаемо для захвата и пассивных звеньев |
| `urdf.not_rendered` | *(предупреждение)* описание — шаблон `.xacro` | разверните `xacro`, иначе сверка не выполняется |
| `urdf.name_differs` | *(предупреждение)* `<robot name>` не совпадает с именем профиля | запуску не мешает; обычно значит, что описание взято от другого робота |
| `limits.length_mismatch` | лимитов не столько, сколько суставов | длина обязана совпадать с `joint_order` |
| `adapter.plugin_not_installed` | *(предупреждение)* плагин не установлен | профиль валиден, но запуск с этим адаптером невозможен |

Предупреждения не мешают запуску. Ошибки мешают, и это осознанно: рассогласование
сред — ошибка валидатора, а не странное поведение робота (инвариант 6).

## Шаг 5. Среды и запуск

```bash
heron gen examples/robots/my_robot/profile.yaml --into generated/my_robot --backend gazebo
```

Одиночный профиль порождается как сцена из одного робота. Бэкенд указывается
явно, когда профиль объявляет несколько адаптеров симуляции: владелец физики
один, и выбрать его должен человек.

Порождается:

| Файл | Что это |
|---|---|
| `my_robot/description.urdf` | ваше описание плюс вклеенный блок `ros2_control` |
| `my_robot/controllers.yaml` | конфигурация контроллеров, выведенная из контракта |
| `world.sdf` | мир со светом, землёй и шагом физики под вашу частоту |
| `bringup.launch.xml` | что и в каком порядке запускать |
| `view.rviz` | конфигурация визуализации |
| `manifest.json` | чем порождено, из чего и при каком `contract_id` |

Для сцены из нескольких роботов пишется сценарий — пример:
[`examples/scenarios/table.yaml`](../examples/scenarios/table.yaml). Там же видно,
что всё именуемое строится от идентификатора робота **в сценарии**, а не от
имени профиля: два экземпляра одного робота не пересекаются ни топиками, ни
системами отсчёта.

Запуск требует Linux с ROS 2 Jazzy и Gazebo Harmonic — [установка](install.md):

```bash
heron sim run examples/scenarios/table.yaml --into generated/table -R examples/robots --dry-run
heron sim run examples/scenarios/table.yaml --into generated/table -R examples/robots
```

`--dry-run` печатает команды и не запускает ничего — это работает где угодно и
показывает состав запуска до запуска.

> Порождённые сцены на настоящем симуляторе пока не проверены: фаза 2 дорожной
> карты не закрыта. Если сцена не поднимается, дело с большой вероятностью не в
> вашем роботе.

## Шаг 6. Зафиксировать контракт

```bash
heron contract lock examples/robots/my_robot/profile.yaml
```

Записывает `contracts.lock.json` рядом с профилем — предыдущее состояние
контракта. С этого момента изменение представления данных **без объявления
`revision`** становится ошибкой валидатора: переставили суставы, поменяли единицы
или частоту и забыли сказать об этом — платформа не даст поехать дальше
([ADR-0006](decisions/0006-contract-canonical-form-and-lock.md)).

Файл `contracts.lock.json` коммитится. Это единственная производная величина,
которую платформа версионирует, и она себя оправдывает: изменение представления
данных видно в обзоре изменений отдельной строкой, а не правкой внутри YAML.

Посмотреть идентификатор и сравнить два контракта:

```bash
heron contract id   examples/robots/my_robot/profile.yaml
heron contract diff examples/robots/my_robot/profile.yaml examples/robots/arm6.yaml
```

При расхождении печатается различие **по полям**, а не факт «хеши разные»:
человеку нужно знать, переобучать политику или править профиль.

## Частые отказы

**Робот не появился в симуляторе, ошибок нет.** Почти всегда — звено с нулевой
массой или вырожденным тензором инерции: Gazebo выбрасывает его вместе с
поддеревом молча. Проверьте `<inertial>` у каждого звена.

**Меши не видны, робот «из палок».** Пути `package://` разрешаются только
средствами ROS 2. Пакет должен быть в `GZ_SIM_RESOURCE_PATH`, либо переведите
ссылки на относительные пути и задайте `mesh_dir`.

**`urdf.joint_missing` на роботе, который точно исправен.** Посмотрите, не
`.xacro` ли у вас в `description.urdf`: шаблон не разворачивается, и сверка идёт
не с тем файлом. Признак — предупреждение `urdf.not_rendered` рядом.

**Все лимиты «шире модели», хотя они из паспорта.** Проверьте `angle_unit`.
Паспорт обычно в градусах, URDF всегда в радианах; платформа переведёт сама, но
только если в контракте написано `deg`.

**`heron gen` отказывается: нет генераторов для бэкенда.** Среды порождаются
пока только для Gazebo. Робот с адаптером под другой бэкенд проверяется
валидатором полностью, но сред для него не строится.

**Меши на месте во входе, а в симуляторе робот без геометрии.** Относительные
ссылки (`meshes/part.stl`) в порождённой копии описания переписываются на
абсолютные `file://` от места входа ([ADR-0017](decisions/0017-generated-description-anchors-meshes.md)).
Поэтому порождённый набор привязан к машине: перенесли каталог или входное
описание — перепорождайте, `gen --check` покажет расхождение.

**Робот лёг на пол: `urdf.free_base_uncontrolled`.** Уровень доступа `low`
отключает встроенный контроллер, а описание не крепит базу к звену `world`.
Платформа базу не закрепляет ([ADR-0018](decisions/0018-free-base-is-a-run-condition.md)):
это условие прогона, и записывать его надо рядом с результатом.

**Описание от производителя в репозиторий не кладётся.** Пример —
[`examples/robots/g1_23dof`](../examples/robots/g1_23dof): рядом с профилем
лежит скрипт, загружающий описание по закреплённому коммиту. Хранится источник,
а не 110 МБ мешей; сменить коммит — значит сменить вход и перепроверить профиль.

**Навык не запускается: `skill.control_mode_incompatible`.** Навык требует
потока команд, а робот принимает движение целиком. Это не настройка, а свойство
интерфейса робота.

## Если производитель дал адаптер и двойник

Путь выше — робот, которым управляет `ros2_control`: платформа порождает для него
интерфейсы, контроллеры и всё остальное. У многих роботов свой протокол — DDS,
сетевой API, собственная прошивка приводов — и свой симулятор от производителя.
Такой робот входит в платформу **пакетом**, устроенным так, будто его прислал
производитель ([ADR-0021](decisions/0021-robot-ships-as-adapter-and-twin.md)).
Живой пример — [examples/plugins/unitree_g1](../examples/plugins/unitree_g1): G1
через DDS производителя, в MuJoCo производителя и в Gazebo, без строки ядра под
него.

### Что в пакете

Пара: **адаптер** на все среды и **сторона двойника** для каждой пары «адаптер,
бэкенд». Обе — точки входа Python:

```toml
[project.entry-points."heron.adapters"]
my_robot_link = "my_robot.adapter:MyRobotAdapter"

[project.entry-points."heron.twins"]
my_robot_mujoco = "my_robot.twin:MyRobotMujocoTwin"
my_robot_gazebo = "my_robot.bridge:MyRobotGazeboTwin"
```

Из платформы пакет импортирует только публичный API — модули `PUBLIC_MODULES` в
`src/heron/public.py`. Тест проверяет это для каждого пакета в `examples/plugins`:
пакет, дотянувшийся до валидатора или CLI, работает и ничего не доказывает.

### Адаптер

Протокол тот же, что у встроенных, — `ControlAdapter`. Сверх методов платформа
ждёт от адаптера вот что:

| Обязанность | Зачем | У G1 |
|---|---|---|
| `requirements`: что процессу нужно и что в нём запрещено | `env check` и `run` назовут недостающее до подключения ([ADR-0025](decisions/0025-environment-requirements.md)) | `cyclonedds ==0.10.2`, запрет `>=0.11`, `unitree_sdk2py` |
| SDK импортируется в `connect`, канал внедряется | решения адаптера проверяемы без SDK ([ADR-0029](decisions/0029-g1-dds-channel.md)) | `CycloneChannel` и записывающий `RecordingChannel` |
| метка состояния — время мира | темп и сторожевой таймер различают часы ([ADR-0015](decisions/0015-executor-paces-and-watches.md)) | `LowState.tick`, мс |
| отказ в команде — `CommandRefusedError`, ничего не отправлено | исполнитель сначала остановит робота ([ADR-0026](decisions/0026-refused-command-stops-the-robot.md)) | позиция вне рамки профиля |
| `emergency_stop` не зависит от свежести состояния | его вызывает сторожевой таймер именно тогда, когда состояния нет | демпфирование, `kp = 0` |
| конфигурация связи — в `params` профиля | между двойником и железом меняется только она (инвариант 3) | `domain`, `interface`, `peers` |
| `supports_speed_scale` на классе | `run` не отдаст шкалу связи, которая её не исполнит ([ADR-0052](decisions/0052-speed-scale-is-a-run-quantity.md)) | `False`: поток не замедлить |

Общий контрактный набор — модуль платформы `testing.adapter_contract`. Пакет
прогоняет его из **своих** тестов, наследуя `AdapterContract` со своей обвязкой
`Harness`: как построить адаптер, какой профиль, как подать показания, а для
командного класса — как робот сообщает конец движения (`finish`). Тесты платформы
пакетов не перечисляют ([ADR-0056](decisions/0056-the-adapter-contract-suite-is-public.md)):

```python
from unitree_g1 import testing
from heron.testing.adapter_contract import AdapterContract, Harness

class TestG1DdsAdapter(AdapterContract):
    harness = Harness(plugin=testing.PLUGIN, make=testing.recording_adapter,
                      profile=testing.profile_23dof, config=dict(testing.LINK_PARAMS),
                      prime=testing.prime)
```

### Двойник

Двойник — другая сторона связи в симуляции: то, что говорит протоколом робота. Он
объявляет пару (`adapter`, `backend`), род и требования; ищется по паре, два на
пару — ошибка ([ADR-0024](decisions/0024-twin-protocol.md)).

- **Род «владеет физикой».** Симулятор производителя сам и есть мир, поэтому сцена
  из одного робота (`twin.owns_physics_not_alone`). Для MuJoCo двойник возвращает
  свои процессы значениями — `MujocoTwin.processes(scene)`; бэкенд `mujoco`
  платформы их запускает и сам MuJoCo не импортирует
  ([ADR-0030](decisions/0030-mujoco-backend-starts-the-twin.md)).
- **Род «мост».** В чужом мире робота исполняет мост — как прошивка на борту
  ([ADR-0033](decisions/0033-gazebo-bridge-is-the-drive-firmware-twin.md)). Для
  Gazebo двойник — `GazeboTwin`: элементы описания, файлы рядом с ним, узлы
  запуска, имена управляющего слоя и окружение мира
  ([ADR-0034](decisions/0034-gazebo-scene-dds-environment-and-names.md)).
  Встроенный путь `ros2_control` — такой же двойник той же группы.

Описание кинематики — вход производителя. Вторым описанием можно объявить MJCF
(`description.mjcf`), и валидатор сверит с профилем оба (`urdf.*`, `mjcf.*`).

### Профиль

```yaml
adapters:
  sim.mujoco: {plugin: my_robot_link, params: &link {domain: 1, interface: lo, peers: [127.0.0.1]}}
  sim.gazebo: {plugin: my_robot_link, params: *link}
  real:       {plugin: my_robot_link, params: {domain: 0, interface: eth0}}
```

Адаптер один, миров три; различаются только `params`.

### Проверка

```bash
heron validate  <профиль> <сценарий> -R <реестр>          # данные: описания, двойник под пару, род
heron env check <сценарий> -R <реестр>                     # машина: требования адаптера и двойника
heron sim run   <сценарий> --into <каталог> -R <реестр> --dry-run   # что запустит мир
heron run       <сценарий> -R <реестр> --dry-run           # связь, топики, окружение мира
```

### Чего платформа за пакет не делает

- **Не порождает мост.** Тип сообщения робота известен при компиляции, и мост,
  «общий и настраиваемый данными», оказался бы общностью производителя, а не
  платформы (ADR-0033). Раскладку и имена мост получает параметрами.
- **Не держит двух роботов с фиксированными топиками в одном домене DDS.** Второй
  такой в сцене — отказ генератора (ADR-0034).
- **Не закрепляет свободную базу и не включает страховку двойника.** Робот,
  падающий до первой команды, — условие прогона, объявленное валидатором
  (`urdf.free_base_uncontrolled`,
  [ADR-0018](decisions/0018-free-base-is-a-run-condition.md)).

## Чеклист

```
[ ] Описание .urdf есть, шаблон развёрнут
[ ] У каждого звена ненулевая масса и невырожденный тензор инерции
[ ] Одно корневое звено, меши разрешаются
[ ] joint_order = вектор управления, имена совпадают с описанием
[ ] angle_unit соответствует единицам лимитов
[ ] Лимиты профиля уже пределов модели
[ ] Возможности — только то, что робот действительно умеет
[ ] control_mode отражает интерфейс робота, а не желание
[ ] Адаптер под бэкенд сцены объявлен
[ ] heron validate — ошибок нет
[ ] heron gen — среды порождаются
[ ] heron contract lock — контракт зафиксирован и закоммичен
```
